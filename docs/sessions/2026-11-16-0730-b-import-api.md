### Key decisions
- **One plan for both sides.** The API and DemoStore run the same shared `planImport` and kind rules on their own records. The server never parses a file: the browser turns it into text cells and sends only the mapped columns as JSON; the API re-reads every cell with `readCell` and stores no file.
- **Access.** `settings.import.manage`, company-wide data scope, the kind's own view, create and edit keys, and the sensitive key of any sensitive column mapped. The company only from the session; a body naming a company is a 400.
- **What you saw is what you get.** Commit and Undo need a step-up. The commit runs in one transaction under a per-company advisory lock and `SHARE ROW EXCLUSIVE` table locks, re-plans against current records, and is refused (409 `plan_changed`) if any row's action differs from the dry run's.
- **Exact Undo.** Refused unless every record still equals what the import wrote, every reference it puts back is live, and no live record refers to a created one (foreign keys from the catalog plus the polymorphic links). Created records are soft-deleted.
- **Audit.** One entry per record and one per batch, in the same transaction; saved columns are audited too. The dry run writes nothing.

## Decisions and why
Each goes into ADR 0057 "Safest options taken", the blueprint-delta row and the spec's "Real build" section.

1. **S-1 Part 1 only** (customers, addresses, suppliers, products); the API answers 404 for the other kinds. Why: none of them posts to the ledger or touches pay, their loaders exist on the API, and Undo can be exact for them.
2. **S-2 Company-wide scope.** Why: matching reads every record (otherwise an existence oracle), and a row may set another rep, which moves the customer's "own" scope.
3. **S-3 The kind's own keys** on top of `settings.import.manage`; products also need `purchasing.supplier.view` and `inventory.product.view_sensitive`. Why: nobody grants more than they hold.
4. **S-4 Sensitive columns** (credit limit, cost) need the key that reveals them; a supplier's credit limit needs both the customer-credit key and a supplier-money key. Why: rule 5.
5. **S-5 Stock history freezes a product's cost, category, unit, coverage and width,** for the import and for Undo; stock in transit counts. Why: cost follows receipts and average cost; changing it under stock would break inventory value.
6. **S-6 Retired SKUs are refused,** because `products_sku_uidx` is not partial on `deleted_at`.
7. **S-7 Step-up for commit and Undo;** `MFA_REQUIRED_KEYS` unchanged (an auth change is the owner's).
8. **S-8 Active reps only.**
9. **S-9 Strictest terms:** a new supplier without Terms gets Pay on order (the module's default, not the spec's Net 30); a new customer gets Due on receipt (the spec), never the company default.
10. **S-10 What you saw is what you get** (the `expected` action string); all valid rows commit or none.
11. **S-11 Idempotent re-imports:** decimals compared as decimals, a supplier address by its four fields, categories as a set.
12. **S-12 Limits:** only mapped columns; 2,000 rows, 60 columns, 1,000-character cells, module field lengths and digit caps; a 100 KB request (body limit unchanged); one import operation at a time per company; 50 commits per 24 hours; a 10-second lock timeout.
13. **S-13 More audit:** per record plus per batch; saved columns audited (rule 10).
14. **S-14 Undo stays exact** (above).
15. **S-15 Nothing leaves that needn't:** batches never carry `changes`, `savedBy` is dropped, `Cache-Control: private, no-store`, no file stored, the wizard's own CSVs neutralise formula cells.
16. **S-16 Ambiguous keys refused:** an External ID, email, name or SKU matching more than one record is a row error, never "the first one".
17. **S-17 Hidden control characters refused** in cells (except tab and line breaks in a timesheet note), headers, file names and mappings.
18. **S-18 Product rules:** coverage and width more than 0; cartons need coverage in every category; carpet needs a width; prices and costs fit `numeric(14,4)` after conversion; a supplier that matches exactly one record.
19. **S-19 Blank means blank in the chosen columns,** in both modes.
20. **S-20 Sensitive columns are never auto-mapped** for someone who can't use them.

Not taken: escaping formula cells in the app-wide `data-table/csv.ts`. It is shared by every list export and needs its own rule for negative numbers; it stays an open STATUS item (owner question 11).

## Decisions taken during the build
Each is in ADR 0057 ("Also safer, settled while building", "Smaller choices made while building", "For the owner") and, where it changes behaviour, in the delta row. The planned ones are under "Decisions and why" above.

### Shared (stage 1)
- **Emails match exactly, ignoring case only.** The plan folded every key, which would treat "j-smith@" and "j_smith@" as one person and update the wrong customer. External IDs and names still fold; SKUs compare in lower case, as before. Safer; a test covers it.
- **`canonical.ts` holds the content comparison** (`sameRecord`), apart from `undo.ts` to avoid an import cycle. `patched` uses it too, so a different key order (jsonb sorts keys) never counts as an update.
- **`ImportUser.branchId` is optional,** set only by the demo for its opening invoices; without it that kind wouldn't compile or would change behaviour.
- **SR-22 contradicted itself:** coverage allows 3 decimals (numeric(14,3)), so `0.0001` is refused; the test checks that and uses `0.001`.
- **Trailing zeros are not decimals** in the number limits ("23.6400" passes 3 decimals); money keeps the spec's two-decimals-as-typed rule. A stored coverage of 0 counts as missing, so nothing divides by it. A choice naming an empty header counts as no column. The batch summary is built field by field.

### Demo parity (stage 2)
- **The contract types moved to shared here, not in stage 5,** because `DemoStore implements ApiClient` wouldn't compile with types that require `changes`.
- **Undo in the demo checks the import's access** (the kind and the batch's stored mapping) after the gone and already-undone checks, as the API does. Safer; the plan's 5.3 didn't list it.
- **`productUndoProblem` is shared,** so the demo and the API refuse a product Undo with the same words (stock history, a removed earlier supplier).
- **Saved columns in the demo** need the kind open, refuse unknown fields and are audited ("Saved import columns", rule 10).
- **The demo hides kinds whose switch is off,** for the platform admin too (rule 13); `importKindsFor` never did. `expected` stays optional in the demo.

### API (stage 3)
- **Writes use row functions, not the module services,** which open their own transactions and don't write credit limit, rep, external ID, categories or products. The loaders, audit shapes, `contactProblem` and `lockStock` are reused. No kind had to be cut.
- **`kind-stores.ts` holds the store registry,** apart from `kind-store.ts` to avoid an import cycle. The product Undo check reads the stock facts once per batch.
- **`GET /imports` lists saved columns only for the kinds the person may import** (the plan listed every live row). Safer.
- **An empty external ID is never stored** (`|| null`; the plan had `?? null`, which would keep `""`).
- **Column-choice keys are checked on the whole mapping** (Zod 4 replaces per-key messages): a control character gets the control-character words; a key over 60 characters, and a `__proto__` key checked on the raw body, get "The column choices name a field this import doesn't have.".
- **New words:** an unknown body field, "The request has a field this import doesn't take."; an import without `expected`, "Check the file again before importing.".
- **The saved-columns audit entry keeps the column objects** on the API; the demo writes a text summary.
- **Smaller:** `now` is the company's local minute (`minuteIn`); a batch whose creator's sign-in is gone shows "Former user"; an import that would change an existing supplier contact stops with an error (the kind never does that); Undo's `ParseUUIDPipe` answers 400 before the switch's 404, as on other routes.

### Final review round
- **Undo locks the rows it removes (security, should fix).** The table locks let a foreign-key insert elsewhere through, and the soft-delete `UPDATE` takes `FOR NO KEY UPDATE`, which doesn't conflict with the insert's `FOR KEY SHARE`; so a quote still being saved for an imported customer was invisible to the reference check, and both committed. Undo now runs `SELECT … FOR UPDATE` on every created record and created part right after the table locks (`lockTargets` in `import-references.ts`: table names only from `REFERENCE_TABLES`, ids as parameters in chunks of 1,000, id order). It waits for the writer within the 10-second lock timeout (409 `import_busy` past it), and the reference check, a new READ COMMITTED statement, then sees the committed quote and answers 409 `import_in_use`. Only the batch's rows are locked. Kept inside the imports module; `createdRows` now feeds both the lock and the check. The writer-side `FOR SHARE` and re-check stay the follow-up (owner question 10), as does a polymorphic link (meeting guest, attachment, outbox row), which takes no lock on the record. New I-32: a quote inserted in an open transaction on a second connection, Undo fired, the test waits until `pg_blocking_pids` shows the Undo blocked on that connection (at most 5 s), commits, and expects 409 `import_in_use`, the waiting observed, and nothing undone.
- **An empty Address type keeps the stored label (correctness, should fix).** `resolveAddress` used "job_site" for a row without a type even when the street and ZIP matched a stored address, so a file without that column relabelled a billing address as a job site, made it the default job site when there was none, and showed "update" instead of "Already on file." (rule 7). The stored label is now kept; only a new address defaults to a job site. Default = yes uses the kept label. The demo runs the same code. New SR-29 (three cases) and I-33 (a dry run on the API, with and without Default = yes).
- **Company A now commits 31 files in the integration file** (I-32 and I-33 add one each), under the 50-a-day cap.
