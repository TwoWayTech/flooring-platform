## Decisions and why
1. **The flows join the existing api-mode suite** (`tests/e2e-api/flows`, tag `@flow`), with no CI workflow or config setting change. Why: `.github` is the riskiest file to change unattended, and any other placement gives up the regression net on main. Moving them is Q1.
2. **Stage commits carry `[skip ci]`;** only the handoff commit runs CI. Why: the CI budget.
3. **Effects are checked on screen;** `/api-proxy` reads only where no screen exists (trial balance, Outbox, bell) and for F4's cancel. Why: the Outbox and bell screens still show DemoStore rows in api mode, and no trial balance screen exists.
4. **Ledger checks are exact deltas by account code,** with cash as one `isCashAccount` row and a missing account read as zero. Why: `key` can be null, cash can be `bank:<id>`, and a fresh CI database has no accounts until the first posting.
5. **Outbox rows must be `sent` on CI only;** locally a row that isn't is annotated. Why: CI sends through `memory`; the local provider is in the env file, which is never read.
6. **Own data, run ids, deltas only, no seeded document touched.** Why: the local database is reused across runs, and seeded documents posted no journal entries.
7. **Clean-up goes through the product** (void, reopen, deactivate, cancel), on screen in the journey and through registered API calls after a failure; append-only rows stay. Why: CLAUDE.md rules 9 and 10; tests never bypass them.

10. **F3 sweeps its week and rotates its hours.** Why: identical hours are skipped, so a second run in the same week would save nothing.

### Stage 1 (helpers)
23. **The audit time bound is rounded down to the minute.** `GET /audit` gives `at` to the minute in UTC (`audit-log.service.ts:83`, `toISOString().slice(0, 16)`), so the plan's literal `at >= since − 5 s` would miss an entry made in the flow's first minute. `expectAuditRows` takes `since − 5 s` rounded down to its minute. Why: the safer reading; the time bound still excludes earlier runs' rows with the same label.
24. **`ledger.ts` adds `ledgerMismatches` and `movedBy`** to the plan's `netByCode`, `ledgerDelta` and `resolveExpected`. `ledgerMismatches` is the whole ledger rule as a pure function (each expected account by exactly its amount, exactly one cash account for `CASH`, every other account zero), and `expectLedgerMoved` only asserts it is empty. `movedBy` reads one account's move from the books, for F1's cut cost and F2's received value, which no persona can compute. Why: the unit test then covers the real rule, not only the delta.
25. **`resolveExpected` drops zero amounts and throws on a missing account.** A tax of 0.00 can be passed as it is ("left out when zero" needs no branch in a flow); a non-zero move on an account the trial balance lacks fails with the key named, since the posting would have made it.
26. **`waitForAnswer` listens for answers rather than taking the first one,** and takes an optional query match. A throwaway probe (below) failed on its first run: an HR person's home page reads `GET /pay-periods`, that read was still in flight when `openPayPeriodReview` went to `/hr/pay-periods`, the wait took it, and its body was gone ("navigated away from"). The helper now passes over an answer whose body can't be read and takes the next. The query match lets `openBusinessReport` wait for This month's answer only, never the default Last month's. Why: the race would make every flow that opens a screen after another flaky.
27. **`resetAuthAround(emails)` in the kit** registers the `beforeAll` and `afterAll` resets once, instead of each flow file repeating the control URL and both hooks. It fails with a plain message when `CONTROL_DATABASE_URL` is unset.
28. **Persona fixture clean-ups:** they run newest first, then the contexts close. A clean-up answering other than 2xx, 400 or 409, or throwing, fails a test that had passed (it left data behind) and is only noted on a test that had already failed. Why: a silent clean-up failure would leave data unnoticed; a loud one on an already failed test would hide the first error.
29. **`openPayPeriodReview` reuses the page's first review** when the period holding the day is the one the page opens (the `in_review` default), since picking the same option sends no new request; otherwise it picks by index and checks `period.id`. It returns null when no period holds the day.
30. **`expectOutboxSent` waits for at least one matching row and none `queued` or `sending`,** then applies the CI-only `sent` rule.
31. **Types:** `PayPeriodReview` comes from `@/lib/api/contract` as a type-only import (erased at run time; no product file changes); the trial balance and the Outbox row are local types, because apps/api's types aren't importable here and `GET /outbox` answers flat `recipientName` and `recipientEmail`, unlike DemoStore's `OutboxMessage`. Shared types are used for the rest (`AuditEntry`, `BusinessReport`, `PayPeriod`, `InAppNotification`, `OutboxAttachment`, `OutboxStatus`).
32. **`mondayForRun` now uses the shared `mondayOf` and `addDays`** with `companyToday()`, the same result as its own day arithmetic, and its JSDoc says 8 to 84 days (STATUS noted the slip). `meetings.spec.ts` imports `COMPANY_ZONE` instead of its own Denver constant.
