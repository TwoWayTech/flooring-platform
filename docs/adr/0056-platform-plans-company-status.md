# ADR 0056: Plans and company status in the platform console (platform admin part 2)

- **Status:** accepted, 2026-11-15. Built overnight on `feat/platform-manual-billing` (PR #40) under the owner's rule for this queue: follow the spec as the approved behaviour, deviate only in the safer direction (less exposure, deny by default, refuse what can't be done correctly, reversible over irreversible), record each deviation in docs/blueprint-delta.md and here, and defer what needs the owner. The safer deviations, the /feature-change impact summary and the questions under "For the owner" are open for the owner's review.
- **Context:**
  - ADR 0052, "Later parts", part 2: plans as data (list, create, edit, retire), and suspend, reinstate and cancel through a shared `statusAfter`, leaving subscription rows alone, behind a new switch `admin.billing`. Creating or changing a subscription, recording a payment and correcting a period wait for the owner: an `active` row counts as paid, so a subscription created before any payment would give a never-paid company the paid ladder, and a payment would exist only as an audit row and a moved date (CLAUDE.md rule 9).
  - **Why a new number.** ADR 0052 says later parts add sections to it unless, like part 4, they add a feature key; step 3 of `.claude/commands/feature-change.md` asks for an ADR with the next number. Part 2 adds `admin.billing`. 0055 is taken by `feat/reports-api` (`docs/adr/0055-reports-api.md`), so this is 0056 (checked on origin/main and every remote branch before the docs commit).
  - The behaviour is docs/specs/platform-admin.md, "Part 2: plans and company status", drafted as the first step of this run from the outline that stood under "Parts 2 to 4". As with parts 1, 3 and 4, the P11 "stop for my approval" step could not happen overnight, and neither could the confirmation in step 2 of `.claude/commands/feature-change.md`.
  - Blueprint p13 (the control tables `plans`, `plan_modules`, `plan_limits`, `tenant_subscriptions`), p23 (manual billing, step 5: suspended), p24 (plans and limits), p28 (every action in the platform audit log) and p29 (a company that paid and cancels is read only for 90 days).
  - The code as it is at `86c1689`:
    - `plans` has `key` (unique, deleted rows included), `name`, `product_id`, `monthly_price` and `yearly_price` (numeric(14,2), not null) and `active`. `plan_modules` and `plan_limits` have unique indexes that ignore `deleted_at`. A plan with no live limits row gives no limit;
    - `tenants.status` is free text with no CHECK. The trigger `tenants_status_changed` (control migration 0003) stamps `status_changed_at` with `now()`, the transaction's start, on every real status change;
    - the life cycle (`company-lifecycle.ts`, ADR 0033): `suspended` is read only for good when the company ever paid, else read only for 30 days and then locked; `cancelled` is read only for 90 days (ever paid) or 30, then locked; read only starts the moment the status changes; `companyPhase` takes the stricter of the status's phase and the rows' own;
    - the access rule (`access.service.ts`, `access-rules.ts`): a company with no subscription row at all gets every product module only while its status is `trial` (`freshTrial`); with any other status it gets Platform only;
    - TenantDirectory reads `tenants` and every subscription row on every request, with no cache; jobs read through it and skip read-only companies;
    - the access PATCH has no stale-save check and no re-check of the acting admin under a lock ("the last save wins", ADR 0052 question 11). Part 3's support request locks and re-checks the admin's own `platform_admins` row (ADR 0053);
    - the /admin console is outside the standing gate (`app/admin/layout.tsx`; `StandingGate` is in `app/(app)/layout.tsx`), so an admin whose home company is suspended or locked can still open the console and reinstate it.
  - The bounds of this run: no new or altered table, column, index, trigger or migration; no new dependency and no `package.json` or lockfile change; no change in `apps/api/src/core` (auth, tenancy, access). `git diff --stat origin/main -- apps/api/src/core packages/db/src/control packages/db/migrations` stayed empty after every stage. Subscriptions, payments, invoices, period corrections and using a support grant stay out.

### Routes

Two new controllers join the existing `PlatformModule` (no new Nest module, so `app.module.ts` is untouched): `PlatformPlansController` owns `platform/plans`, and `PlatformCompanyStatusController` is a second controller on part 1's `platform/companies` prefix. Both are `@SessionOnly()` and carry `PlatformAdminGuard` and `@PlatformFeature("admin.billing")` at class level, so a handler added to either inherits both. The five action routes answer 200 (`@HttpCode(200)`); only create answers 201. There is no DELETE. `:id` is a UUID (`ParseUUIDPipe`, 400 otherwise) and names control rows only, as in part 1. /platform now has 17 routes on 6 controllers.

### The platform guard: a switch per route (`platform-admin.guard.ts`)
- **`PlatformFeature(key)`** sets the metadata `platform:feature`, read with `getAllAndOverride([handler, class])`. Step 2 of the guard becomes: `admin.access` off, **or the route's own key off**: 404 `not_found`, still before the admin row is read. A route with no key behaves exactly as before. Both switches are read on every request, never at load, because tests flip them at run time.
- So while `admin.billing` is off the nine routes answer 404 to everyone, before the role check and the step-up (CLAUDE.md rule 13), and a non-admin learns only that a switch is off. The guard lives under `modules/platform`, not core.

### The acting admin, checked again under a lock (`admin-lock.ts`)
- **`lockActingAdmin(tx, userId, roles)`** reads the admin's own `platform_admins` row (`active`, not deleted) `FOR UPDATE` as the first step of every plan and status write: no row or an unknown role gives 403 "Only platform admins can use this."; a role the route doesn't allow gives 403 "Only the platform owner role can change this.".
- Under READ COMMITTED the locked row is read again after another transaction that held it commits, so an admin deactivated, deleted or moved to the support role while their write waits gets 403 and nothing is written (P-13, C-18). The guard's plain reads are not blocked.
- Part 3's support request now calls it with `PLATFORM_ADMIN_ROLES`; its private `lockAdmin` is gone, with the same behaviour (`platform-support.int.test.ts` passes with no expectation changed). The test helpers `holdAdminRow` and `waitForLockWaiters` moved unchanged to `apps/api/test/support/admin-locks.ts`.
- **Lock order everywhere:** the admin's own row, then the plan or company row. Nothing locks them the other way.

### Plans (`plans.controller.ts`, `plans.service.ts`; `packages/shared/src/platform/plans.ts`)
- **`PlatformPlan`:** `{ id, key, name, product, monthlyPrice, yearlyPrice, modules, maxUsers, maxBranches, active, companies, createdAt, updatedAt }`. Prices are decimal strings (`"0.00"`); `modules` are the stored ones in catalog order without Platform, a stored hidden module included; `maxUsers` and `maxBranches` are null only for a plan with no live limits row; `companies` is a count of the companies with any subscription row naming the plan, deleted rows included. No subscription, company id or company name leaves.
- **The shared rules,** one copy for the API, the web before the step-up, and the demo: key `^[a-z][a-z0-9-]{1,39}$`; name trimmed, 1 to 80 characters; product `flooring` or `hr`; prices trimmed, `^\d{1,11}(\.\d{1,2})?$`, never a JSON number, compared with decimal.js; modules among the product's visible ones, at least one besides Platform, never `platform` stored; limits whole numbers from 1 to 100,000; a reason of 10 to 500 characters (`adminReasonProblem`, which part 3's support reason now aliases). `planProblem` checks in that order; `planPatchProblem` refuses any field but name, prices, modules, limits and reason, checks each sent field, then the reason, then, for a plan in use, a real change of modules (compared as sets) or of either limit (422). `planChanges` gives only what differs (`"49"` equals `"49.00"`); `planModulesAfter(product, stored, requested)` keeps every stored module the console doesn't offer for that product.
- **Prices are stored and audited with two decimals** (`storedPlanPrice`, decimal.js), so the audit row matches the stored value.
- **Create:** in one control transaction, `lockActingAdmin` (403); `planProblem` (400); the product row, not deleted (400 "Choose Flooring Suite or HR Suite."); then `insert … on conflict (key) do nothing`, so a taken key, a retired or deleted plan's included, gives 409 "A plan with this key already exists. A key can't be reused, even after its plan is retired." and a parallel create of the same key waits on the unique index and gets the same 409; then one `plan_modules` row per module and one `plan_limits` row, each with `created_by` the admin, and one `plan.created` row.
- **Edit:** `lockActingAdmin`; the plan row `FOR UPDATE` (404 "That plan does not exist."), alone, so the product row isn't locked; `planPatchProblem` (400 or 422); a save that changes nothing answers 200 with the plan as read under the lock and writes nothing; otherwise the name and prices, each wanted module row upserted with `deleted_at` cleared and each removed one soft-deleted (a stored module the console doesn't offer is never touched), the limits row upserted on `plan_id`, and one `plan.changed` row. The plan row's lock conflicts with the key-share lock a future subscription insert takes through its foreign key, so the in-use check can't race one. Two edits run one after the other; the last one wins and both are audited (question 46).
- **A plan with no live limits row** (only possible by SQL) gets one only when both limits are sent; one alone answers 400 "Enter a whole number from 1 to 100,000.", so the console never invents the other limit.
- **Retire and restore:** `lockActingAdmin`; the plan row (404); the reason (400); 409 "This plan is already retired." or "This plan isn't retired."; otherwise `active` flips and one `plan.retired` or `plan.restored` row is written. Nothing reads `plans.active` for access.
- **What a plan edit reaches:** the name is read by the Owner's `GET /billing` and the console, so a rename shows on the billing page of every company with a row on the plan; nothing outside the seed reads a plan's prices, and each company's price lives on its own subscription row, so a price change changes nothing any company sees or pays (P-7 pins Summit's billing page); modules and limits reach every company on the plan, so only a plan no company has used can change them; retire and restore reach nothing.
- **The list** leaves out a plan whose product is neither Flooring nor HR (deny by default; the products table holds only those two), orders by product key, name and key, and isn't paged.

### Company status (`company-status.controller.ts`, `company-status.service.ts`; `packages/shared/src/platform/company-status.ts`)
- **The preview** (`GET /platform/companies/:id/status`) reads in one read-only, repeatable-read transaction: the company's `status` and `status_changed_at` with `now()` in one select, then every subscription row, deleted ones included (the columns TenantDirectory reads). So the three are one snapshot and the preview can't write. `companyStatusView` gives `{ companyId, status, statusChangedAt, phase, readOnlyFrom, lockedFrom, actions }`; `actions` is always suspend, reinstate, cancel, each with its refusal or its `next { status, phase, readOnlyFrom, lockedFrom }` from `statusAfter`, then `companyPhase` and `phaseDates` at the database's time. A stored status the console doesn't know previews as `locked` with no dates, as TenantGuard reads it.
- **The bodies** are strict. `expectedStatus` (the status the admin saw, text of 1 to 40 characters, so a stored unknown status still reaches the 422) is checked first, then the reason, both in the controller through `statusActionBodyProblem`, before the company is read. Cancel also takes `confirmName`; suspend and reinstate refuse it as an unknown field.
- **An action** is one control transaction: `lockActingAdmin` (403); the company row `FOR UPDATE` with `now()` in the same select (404); for cancel, the typed name against the locked row's name, trimmed and case-sensitive (400 "Type the company's name exactly to confirm."); `staleStatusRefusal` (409 "This company's status changed meanwhile. Read it again.") when the stored status isn't `expectedStatus` or `now()` is earlier than the stored `status_changed_at`, plus the same check in SQL (`status_changed_at > now()`) to the microsecond, which JavaScript dates drop; every subscription row; `statusAfter` (409 or 422); `update tenants set status, updated_at where id and status = <read>` (the trigger stamps `status_changed_at`; no row is the same 409); one audit row. After the commit the answer is part 1's company detail, read again, whose phase comes from TenantDirectory.
- **`statusAfter`,** the first check that applies:
  1. a stored status that is none of `trial`, `active`, `past_due`, `suspended`, `cancelled`: 422 `rule_broken`;
  2. the transition (409 `conflict`):

     | Current | Suspend | Reinstate | Cancel |
     | --- | --- | --- | --- |
     | `trial`, `active`, `past_due` | `suspended` | 409 "This company isn't suspended or cancelled, so there is nothing to reinstate." | `cancelled` |
     | `suspended` | 409 "This company is already suspended." | `active` or `trial` (step 5) | `cancelled`, unless step 4 refuses |
     | `cancelled` | 409 "A cancelled company can't be suspended. Reinstate it first if it should be suspended instead." | `active` or `trial` (step 5) | 409 "This company is already cancelled." |

  3. no subscription row ever, deleted rows included: 422, with a message for suspend and cancel that names the stop-gap (switch its modules off on its Access page) and one for reinstate; a company with only deleted rows passes;
  4. suspend and cancel never widen: from `companyPhase` itself, the moment the company reaches read only and the moment it reaches locked, before and after; if either would come later, 422 "That would give this company more time before it becomes read only or locked than it has now, so nothing was changed." It fires only for cancelling a never-paid suspension while the status's ladder binds;
  5. the next status: `suspended`, `cancelled`, or for reinstate `active` when the company ever paid (`companyEverPaid`, now exported from `company-lifecycle.ts`, which `companyPhase` calls, with no behaviour change) and `trial` otherwise. `past_due` is never written.
- **How each result reads,** with no new reading code:

  | After | `companyPhase` | TenantGuard on a company route |
  | --- | --- | --- |
  | Suspended, ever paid | `read_only` now; `locked` only when its rows' own ladder locks | GET passes; a write gets 403 `company_read_only` |
  | Suspended, never paid | `read_only` now; `locked` at the change plus 30 days, or sooner when its rows lock first | As above, then 403 `company_suspended`; sign-in and `/auth/context` still work |
  | Cancelled, ever paid | `read_only` now; `locked` at the change plus 90 days, or at the rows' lock if sooner | As above |
  | Cancelled, never paid | `read_only` now; `locked` at the change plus 30 days, or sooner | As above |
  | Reinstated (`active` or `trial`) | The rows' phase: `full` while a row is current | As the rows say |

  Part 4's standing and the Owner's notice read the new status as they read any status ("suspended" or "cancelled" with `lockedFrom`).
- **What an action changes:** exactly `tenants.status`, `status_changed_at` (the trigger) and `updated_at`, plus one `platform_audit_log` row. No subscription row, module override, ceiling, product, member, session, branding, maintenance flag or `tenant_databases` row changes, and no company database is opened (C-15, C-16). Cancel deletes nothing; reinstate undoes it, and the rows then give the phase. It takes effect on the company's next request and job; a request already past TenantGuard finishes, as with maintenance (ADR 0033). Sessions are not revoked.
- **The company's own audit log is not written.** Reaching it needs a TenantContext from the verified session (CLAUDE.md rule 2), and lint keeps tenancy out of `modules/platform`. The platform audit log is the record; the Owner learns of the change from part 4's standing and notice (question 42).

### Audit (`packages/shared/src/platform/audit-details.ts`, `platform-audit-query.service.ts`, `platform-audit.controller.ts`)
- **Seven new actions,** all by a platform admin: `company.suspended`, `company.reinstated`, `company.cancelled` (target `tenant`; `before { status, statusChangedAt }`, `after { status, statusChangedAt, reason }`; details `status_changed`), `plan.created` (no company, target `plan`; `after` the nine fields; details `plan_created`), `plan.changed` (the changed fields before and after, plus `reason`; details `plan_changed` with `changes { field, from, to }[]`), `plan.retired` and `plan.restored` (`before { active }`, `after { active, reason }`; details `plan_active`). `PLATFORM_AUDIT_ACTIONS` lists 13 and `PLATFORM_ADMIN_AUDIT_ACTIONS` 9.
- **Allow-listed exactly:** statuses among the five, ISO moments, keys, names, prices, modules and limits by the plan rules' patterns, and a reason of 1 to 500 characters or null. A status entry's new status must fit its action (suspended, cancelled, or active or trial for reinstate) and differ from the old one; a retire or restore entry must flip `active` the way the action says. Anything else reads "Details hidden". `companyStatusAuditBody` and `planAuditBody` build the rows for the API and the demo, so both write the same shapes.
- **Reasons** go to the owner role and the entry's author only (`seesAdminReason`; `seesSupportReason` delegates to it). For any other viewer, another admin's row of the seven has `after` selected as `jsonb_set(after, '{reason}', 'null', false)` when it is an object, else null, so the text never reaches the API's memory; the shared view nulls it again. The support role still sees its own reasons (A-9).
- **The filter while the switch is off:** `BILLING_AUDIT_ACTIONS` lists the seven, and `platformAuditActionOn(action)` is false for them while `admin.billing` is off, read on every call. The API's `action` check (`.refine`), the demo's `demoAuditPage` and the web's Action filter use it: filtering by one of the seven answers 400 "Choose an action from the list.". Stored rows of the seven still list and render (question 47).
- Reads are not audited; a refusal writes nothing; a plan save that changes nothing writes no row.

## Safest options taken (also in docs/blueprint-delta.md)
1. **A fresh trial can't be suspended or cancelled, and a company that never had a plan can't be reinstated, from the console (422).** The access rule would leave a suspended or cancelled company with no subscription row with Platform only, so its people couldn't read or export during the read-only days ADR 0033 promises. Fixing it is a core/access change that widens access, which the overnight rule doesn't allow (question 34). The refusal and the page name the stop-gap: switch its modules off on its Access page (reversible, audited).
2. **Suspend and cancel never widen.** The shared check refuses any action that would make the company read only or locked later than it already would be, from `companyPhase` itself, with no second copy of the ladder. Suspending a cancelled company is refused outright (question 37).
3. **Reinstate restores what the rows say:** `active` if the company ever paid, else `trial`. `past_due` is never written, so a company suspended from `past_due` loses its overdue notice when its rows are current; its access doesn't change (question 35). Reinstating after a cancel is allowed, because cancel deletes nothing and touches no subscription row (question 36).
4. **Cancel changes only `tenants.status`, its stamp and `updated_at`,** plus one audit row, and needs the company's name typed exactly. Nothing is deleted, revoked or detached.
5. **A plan in use keeps its modules and limits.** In use means any subscription row, a deleted one included, names it. Name and prices may change: a rename shows on every such company's billing page, and a price changes nothing any company pays. Per-company changes stay on the Access page (question 38).
6. **No plan is ever deleted.** Retire and restore only, both reversible, neither changes a company. A key is never reused (questions 44 and 45).
7. **Every new plan names every field:** both prices typed by the admin (0.00 only as typed, no default, no "yearly is ten months" rule), at least one module, and both limits from 1 to 100,000. "No price" needs nullable price columns (a migration) and "unlimited" an owner decision (questions 39 and 40).
8. **`admin.billing` hides everything when off,** answering 404 before the admin row is read, through a route-level switch in the platform guard, so neither the role check nor the step-up reveals the routes.
9. **Every write: the owner role, a step-up, a reason of 10 to 500 characters and one `platform_audit_log` row in the same control transaction,** under row locks (the admin's own row, then the company or the plan). State checks run under the lock, so two admins can't both apply the same action.
10. **Reasons are seen by the owner role and their author only,** narrowed in SQL first and by the shared view again (question 41).
11. **No company database is opened** and the company's own `audit_log` isn't written (CLAUDE.md rule 2; question 42).
12. **The console shows the consequences before the step-up:** the preview is computed on the server from every row, deleted ones included, at the database's time; a refused action is disabled with its reason; the shared input checks run before any code is asked for.
13. **Both new GETs send `Cache-Control: no-store`.**
14. **The api-mode e2e touches only Summit's status and its own `e2e-` plans.** No helper switches a trigger off on the shared database; `clearTestStatus` moves Summit from `suspended` or `cancelled` to `active` only, and `removeTestPlans` hard-deletes only `e2e-` plans that no subscription row names, deleted rows included, and throws before deleting anything otherwise.
15. **A status action carries the status the admin saw** (`expectedStatus`). If another admin changed it meanwhile, or a later change won the race, it answers 409 and writes nothing. This is stricter than the access PATCH's "last save wins".
16. **The acting admin is checked again under a lock on their own row** in every plan and status write: deactivated, deleted or moved to the support role meanwhile gives 403.
17. **While `admin.billing` is off, the audit log doesn't offer the seven actions as a filter,** in the web, the demo and the API. Their rows stay listed as history (question 47).

**Safer still, settled while building:**
- **Unreadable values deny.** A stored status the console doesn't know previews as `locked` with no dates; `staleStatusRefusal` refuses a moment it can't read; `confirmNameProblem` refuses an empty name even when the company's name trims to empty.
- **The audit allow-list is tighter than the plan:** a status entry's new status must fit its action and differ from the old one, and a retire or restore entry must flip `active` the way its action says.
- **`planModulesAfter` keeps every stored module the console doesn't offer for the plan's product,** a hidden one or another product's, not only hidden ones.
- **Plans:** the list leaves out a plan whose product is neither Flooring nor HR; creating needs a product row that isn't deleted; a plan with no limits row gets one only when both limits are sent.
- **The preview** reads in one read-only, repeatable-read transaction and refuses any query parameter, as `GET /platform/plans` does (the spec said so only for plans).
- **The stale check also runs in the database** (`status_changed_at > now()`), so a race inside one millisecond is caught too; `now()` is read in the same select as the locked row.
- **The web never guesses:** the new plan dialog starts with no product chosen and no price placeholder, limits take whole digits only (so "1e3" or "5.5" are refused), and an edit that changes nothing sends nothing and asks for no code ("Nothing changed, so nothing was saved.").
- **Contrast:** the Status page's Cancel button and the cancel dialog's Continue draw their text with the `text-danger-ink` token (about 5.6:1 in light, 4.6:1 in dark), because the shared destructive button's red on pale red failed axe at 4.18:1 and 3.41:1.

## Smaller choices made while building (not safety)
- **Body check order:** `expectedStatus` first, then the reason, then cancel's name, which is the spec's refusal order and what the strict schema gives (plan 1.4 had put the reason first).
- **Signatures:** `companyStatusView(companyId, current, facts)`, because `PlatformCompanyStatus` holds the id; `planModulesAfter(product, stored, requested, visible?)`; `CompanyStatusAction` in `types/platform.ts` and `COMPANY_STATUS_ACTIONS` in `company-status.ts`. Extra shared helpers so the API and the demo use one copy: `companyStatusAuditBody`, `COMPANY_STATUS_AUDIT_ACTIONS`, `LIFECYCLE_STATUSES`, `isLifecycleStatus`, `newPlanValues`, `storedPlanPrice`. `COMPANY_STATUS_ACTION_LABELS` is the one word per action that the Status button, the dialog title and the step-up label share; review round 1 found three copies of it. `visibleModuleKeys` in `access-patch.ts` is now exported, with no behaviour change.
- **Taken key** by `insert … on conflict do nothing`, not a pre-check or a caught 23505, so a parallel create gets the same 409 with no copy of the HR module's error helper.
- **Refusal order on plan writes:** body shape (400), the admin under the lock (403), the plan (404), the field rules (400), then 409 or 422. Retire and restore check the reason after the 404 and before the 409. Every refusal writes nothing, so the order changes no outcome.
- **"In use"** is the plan's company count, which counts every subscription row, deleted ones included.
- **Web:** on edit the key and product show as plain facts, not read-only inputs, so focus starts on Name; edits send only the changed fields, and a stored hidden module is neither shown nor sent; a 409 on retire or restore closes the dialog and reads the plans again; restoring reads "Restoring marks the plan as offered again. It changes no company."; the in-use note says "1 company" or "{n} companies"; after a status change focus moves to the "Status" heading after 250 ms, because the button may be gone; the status dialog's dismiss button reads "Go back", so it can't be confused with the Cancel action; both pages read again in place by bumping a counter, so the table stays on screen; the audit filter's options come from one helper (`auditActionOptions`).
- **Demo:** `changePlatformCompanyStatus` refuses an action outside the three with "That action does not exist." (the types already prevent it).
- **The e2e restore** sets Summit's status only; the trigger stamps a new `status_changed_at`, and the exact old stamp isn't restored, because that would need `backdateStatusChange`, which switches the trigger off and is for throwaway databases only.

## For the owner
Also in docs/specs/platform-admin.md, "Waiting for the owner", numbers 34 to 47. Questions 1 (the admin host), 2 (using a support grant), 4 (the company's own audit log), 7 (billing) and 11 (stale saves) of ADR 0052 stay open, and the questions of ADR 0053 and 0054 still stand.

34. **Suspending or cancelling a company that never had a plan.** Taken: refused (422); the stop-gap is switching its modules off on its Access page. Or should the access rule change so a suspended or cancelled company with no rows keeps its products' modules, read only (a core/access change)?
35. **Reinstate's status.** Taken: `active` when the company ever paid, else `trial`; a company suspended from `past_due` comes back `active` and loses its overdue notice when its rows are current. Or the exact status before the suspension, read from its audit row?
36. **Reinstate after cancel.** Taken: allowed, because cancel deletes nothing. Should cancel be final?
37. **Cancelling a never-paid suspended company** when it would restart its read-only days. Taken: refused. Confirm.
38. **A plan change for the companies on it.** Taken: a plan in use keeps its modules and limits; per-company changes stay on the Access page. Or should a plan change apply to every company on it at once, after a confirmation?
39. **Prices.** Taken: required and typed, 0.00 allowed as typed, no "no price" without a migration, no yearly = 10 x monthly rule. Confirm, and say what a $0 plan means (question 7).
40. **Unlimited plans and employee bands.** Taken: not creatable. A plan with no limits row, only possible by SQL, means no limit today.
41. **Reasons on status and plan entries.** Taken: the owner role and the author see them; the support role sees "Reason hidden". Confirm.
42. **Telling the company.** Should its Owner be emailed, or see an entry in the company's own audit log, when it is suspended, reinstated or cancelled? Taken: neither; the Owner sees part 4's standing and notice (also question 4).
43. **The new key `admin.billing`.** Confirm status `demo`, both products, the Platform module and writes by the owner role only, and the retitle of `admin.access` to "Platform admin: companies, modules and ceilings". The impact summary is above.
44. **Retired plans in the list.** Retiring a plan changes nothing today, because subscriptions can't be created yet. Taken: listed and marked Retired. Should they be hidden by default?

## Residual risks
- **Clock skew.** The trigger stamps the database's clock, and TenantGuard compares with the API's. If the API's clock runs behind the database's, a cancelled company, or a never-paid suspended one, reads `full` for that gap after the change. A paid suspension is read only whatever the time.
- **Reinstate gives time back.** Reinstating restores full use, and a later suspend starts a new 30 days within the rows' own ladder; it never gives more than the rows allow, because `companyPhase` takes the stricter of the two. Each step is an owner-role write with a step-up, a reason and an audit row.
- **Owners get no email** and no entry in their own audit log (question 42).
- **The demo's company side has no life cycle:** a company suspended in the demo console keeps working on its own side and stays on the demo sign-in list. In the demo a plan rename doesn't show on the console's companies list, because each demo company keeps its own plan name; on the API it does.
- **Demo order:** for a plan that doesn't exist, the demo checks unknown PATCH fields after the 404, while the API refuses them first. The web never sends unknown fields.
- **`featureForPath` attributes /admin/plans to `admin.access`** (wildcard ranking). The admin pages check `admin.billing` themselves, and nothing under /admin uses `pathOn`.
- **The plan list isn't paged** (a handful of plans).
- **History stays visible:** audit rows of the seven actions still list while `admin.billing` is off (question 47).
- **The SQL reason narrowing isn't tested on its own.** The shared view nulls the reason again, so over HTTP A-9 shows only the end result, as for the existing `support.requested` narrowing.
- **Each local api-mode e2e run** adds four rows to `platform_audit_log` (append-only). A killed run can leave Summit suspended until the next global setup, and an `e2e-` plan until the next clean-up. Moving Summit back stamps a new `status_changed_at`, which doesn't change an `active` company's phase (locally it moved from 2026-11-14 22:43:37 UTC to 2026-11-15 21:24:12 UTC).
- **Plan names aren't unique;** the key tells two plans apart.
- **In use is "ever named",** so a plan used once keeps its modules and limits for good.
- **The `freshTrial` rule** stays as it is (question 34), and a fresh trial still has no end (STATUS, "Trial with no subscription stays `full`").
- **The access PATCH** still has neither an actor re-check under a lock nor a stale-save check (question 11); part 2's writes have both. A follow-up.
- **Admins can type company data into a reason.** The hint discourages it, and the support role can't read other admins' reasons.
- **The shared destructive button** in packages/ui draws red text on a pale red background below 4.5:1 (4.18:1 light, 3.41:1 dark). Part 2 fixed only its own two buttons; `components/reason-dialog.tsx`, the invoice, purchasing and contract screens and `import-history.tsx` use the same style. A follow-up for packages/ui, checked with axe on every screen that shows one outside a dialog.
- **The whole Flooring demo project runs in CI only** for this PR (see "End-to-end coverage").
- **Merge with `feat/reports-api`:** both add a delta top row, STATUS and BRANCHES entries, and blocks in `contract.ts`, `api-methods.ts`, `store.ts`, `packages/shared/src/index.ts` and docs/api-contract.md. The blocks are separate and commented; the second to merge keeps both.
