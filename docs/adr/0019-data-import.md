# ADR 0019: Data import with Papa Parse and SheetJS, planned in shared code, with Undo

Date: 2026-11-09. Status: accepted.

## Context
Feature batch 2, Batch G1: an import wizard for customers, customer addresses, suppliers, products, rolls and stock, open customer invoices, open supplier bills and employees, from CSV or Excel (10 MB), parsed in a Web Worker, with saved column mappings, validation per row and cell, a preview and dry run, an error report, and an import history with Undo. Records match on external ID, SKU or email, so a second import updates. The spec names Papa Parse and SheetJS (installed from its official CDN package, not the outdated npm release).

## Decision
- **Libraries.** `papaparse` 5.5.3 reads and writes CSV; `xlsx` 0.20.3 from `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz` reads and writes workbooks (the npm `xlsx` stops at 0.18.5 with known issues). Both load only inside `features/import/parse.worker.ts`, a Web Worker started per request and ended with the answer, so they never reach the main bundle and a large file never freezes the page. The worker also writes the CSV and Excel templates and the error report.
- **Rules in shared code.** `packages/shared/src/import`: field definitions per kind (`kinds/*.ts`: label, type, required, aliases, choices, unit, template examples), cell reading (`fields.ts`: money with at most two decimals, numbers with their unit such as "12 ft", whole numbers, ISO and US dates, yes or no, choices by label or value, lists), header auto-matching (`mapping.ts`), and `planImport`, the dry run: rows are read, repeats within the file flagged, and each kind matches the row against the company's records to create, update (only the cells given) or skip it. Rows are planned in order on a working copy, so two addresses for one customer build on each other. The plan lists every change with the version it replaces.
- **Matching.** Customers: external ID, then email (one is required). Suppliers: external ID, email, then name. Products: SKU. Rolls: roll number; boxed stock: SKU and warehouse, read as a count, so the import writes one stock movement for the difference, sourced to the import (`count`, IMP number) and on hand stays the sum of movements. Open invoices: invoice number, one untaxed "opening balance" line, sent on the issue date, due by the customer's terms unless given; an invoice made in the app or one with payments is left alone. Open bills: supplier and bill number, no PO; one with supplier payments is left alone. Employees: email, then external ID. `Customer`, `Supplier` and `Employee` gain an optional `externalId`.
- **Store.** `ApiClient.importOverview / previewImport / runImport / undoImport / saveImportMapping` take the company id: a user of the open company needs `settings.import.manage` (Owner by default) and may import only there; with no company open the caller is the platform admin, whose pages close the company first (`closeCompany`). Kinds follow the company's modules (employees need HR). The store plans every request again, imports only valid rows, refuses an import with nothing to write, and keeps an `ImportBatch` (IMP-1001…) with the counts and changes; `importBatches` and `importMappings` are new collections, empty in the fixtures. Undo removes created records and restores replaced ones, and is refused when any of them changed since or a new record is already used elsewhere. Imports and Undo are audited under Data.
- **Demo limits.** 10 MB per file, 2,000 rows per import (the overlay lives in browser storage), first sheet of a workbook.

## Consequences
- The real API runs the same `planImport` on the server against the database, with batches in a table and the error report from the same rows.
- Imported products start with a neutral swatch; customers have no certificate, so tax exemption is not imported.
