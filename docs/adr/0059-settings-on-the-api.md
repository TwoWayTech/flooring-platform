- **Context:**
  - Week 5's Settings module (docs/real-build-plan.md, module order row 4) was never built. The API has a company `settings` table with one row per group (`settings_group_uidx`), seeded for Summit, and its modules act on those rows: customer payments, write-offs and supplier payments read `payments` (`loadPaymentSettings`), expenses read `expenses` (`loadExpenseSettings`), and emails and refusal texts read `numbers` (`loadMoneyFormat`). The only settings route was ADR 0040's `GET/PUT /settings/accounting`, which has no screen.
  - **The silent no-op.** `getSettings()` and `updateSettings()` were not in `API_METHODS`, so in api mode every Settings page read and saved DemoStore's copy in the browser. An Accountant who turned the two-person check on, changed the write-off limit or set expense approval saw "Payments saved" while the server kept applying its old rows, for money in (customer payments, write-offs) and money out (supplier payments).
  - **A reserved name.** `unitCost` is in `SENSITIVE_FIELDS` (product cost, ADR 0031), and the number format's `decimals` record has a `unitCost` kind. The global interceptor strips it at any depth for anyone without product cost, the HR Suite Owner included (that key is a `core` key).
  - STATUS: B6's note that tax rates are numeric(18,8) and answered raw (part 3); "Settings default inputs keep a bare point"; "When `PUT /settings/:section` moves to the API, it must refuse `overtimeRuleProblem`"; "Settings at provisioning"; GET /company's D12 (the shell's number format and branding are still DemoStore's) and its note that the time zone has two copies (`tenants.time_zone` and `localization.region`).
  - Precedents: `StepUpService` (roles, users, support grants, import; ADR 0034 and 0057), `AuditService.record` in the caller's transaction (ADR 0031), `AccountingService.save` (insert with `onConflictDoUpdate` on the group), `requireFeature` (`sales-common.ts`), the transport's re-read after every answered write (ADR 0051, 2026-11-16), and GET /company's shell query (ADR 0051 "GET /company").

Code comments cite this ADR by label: `D1` to `D24` are the decisions below, and `Q1` to `Q10` the owner questions.

## Decision

### 1. Scope: six parts, part 1 first (D1)
All of Settings is too big for one review: nine sections, the locations collection, versioned tax tables, a control-database time zone and branding row with a logo upload, and the payroll lock. Part 1 is the settings read plus four plain JSON sections with no side effects: **Company profile** (printed on every document), **Number format** (every `<Num>` and the money in emails), **Payments** (the two-person check, the write-off limit and the prefixes, which customer and supplier payments read on the server) and **Expense approval**. It builds the module, the read, the write pattern, the shared rules table and the web's served-sections switch that later parts extend, and it ends the silent no-op on two fraud controls.

### 2. Shared (`packages/shared/src/settings`, no new dependency; D8)
- **`sections.ts`**
  - `SETTINGS_SECTIONS`: per section, the keys that save it (any one), the feature switch of the page that saves it, the module whose absence refuses the save, and the audit label. It replaces DemoStore's `SETTINGS_PERMISSIONS` and `SETTINGS_LABELS`; the API's decorators spread its keys and module (D19, CLAUDE.md rule 4). Payments is `core` although its key is a `platform` key: the payments feature belongs to Flooring, and `/settings/accounting` takes the same key with module `core`. The two `localization` keys are the demo's whole-section rule; API routes go per tab (parts 2 and 3).
  - `API_SETTINGS_SECTIONS = ["profile", "numbers", "payments", "expenses"]` and `isApiSettingsSection`: the sections the API serves. A later part adds its section here and to `SETTINGS_READERS`, and the web routes it with no other change.
  - `SETTINGS_READERS` and `readableSections`: who reads which section (D3); `profileFor`: the EIN only for `settings.company.manage`; `SETTINGS_SCOPE_MESSAGE` ("Company settings cover the whole company.").
  - The number format's wire (D6): `NumberSettingsWire` with `decimals: { kind, places }[]`, `numbersToWire` (kinds in `NUMBER_KINDS` order) and `numbersFromWire` (tolerant, for the web's read only: an unknown kind is dropped, a missing or non-integer one takes its default). `SettingsAnswer`.
- **`section-rules.ts`**: the content rules, with the words both modes show. `companyProfileProblem`, `numberSettingsProblem(next, current)` (each kind once and in range, the negative style, compact dashboards, and the locale and currency unchanged: D12), `paymentSettingsProblem` (amounts empty or `MONEY_TEXT`, prefixes `DOCUMENT_PREFIX_TEXT`, payment and refund prefixes different ignoring case: D18), `expenseSettingsProblem`, and the dispatcher `settingsSectionProblem(section, value, current)`, which also carries `localization`'s overtime check, moved out of DemoStore. The patterns (`EIN_PATTERN`, `EMAIL_TEXT`, `WEBSITE_TEXT`, `DOCUMENT_PREFIX_TEXT`) and message tables are exported, so Company profile's form builds its inline checks from them.
- **`decimal-text.ts`**: `MONEY_TEXT = /^\d{1,12}(\.\d{1,2})?$/`, plain unsigned money: no bare point, sign, exponent or space.

### 3. The API (`apps/api/src/modules/settings`; D2)

| Route | Guards | Handler checks, in order | Answer |
| --- | --- | --- | --- |
| `GET /settings` | `@AnyCompanyMember()`, `Cache-Control: no-store` | none | `SettingsAnswer`, cut for this person |
| `PUT /settings/profile` | `settings.company.manage` | switch `settings.company` (404) → data scope `all` (403) → strict body (400) → `companyProfileProblem` (400) → save | the saved profile |
| `PUT /settings/numbers` | `settings.numbers.manage` | switch `settings.number-format` → scope → strict body, each kind once → `numberSettingsProblem` against the stored format → save | the saved `NumberSettingsWire` |
| `PUT /settings/payments` | module `core`, then `settings.payments.manage` | switch `sales.payments` → scope → strict body → `paymentSettingsProblem` → **step-up** (403 `step_up_required`) → save | the saved `PaymentSettings` |
| `PUT /settings/expenses` | module `core`, then `settings.expenses.manage` | switch `finance.expenses` → scope → strict body → `expenseSettingsProblem` → save | the saved `ExpenseSettings` |

- **Explicit paths, not `:section`** (D2): each route declares its own permission and module, so the route inventories (`permissions.int`, `isolation.int`) see them, an unknown section is Nest's 404, and nothing clashes with `@Controller("settings/accounting")`.
- **Strict bodies** (`settings-input.ts`): Zod `.strict()` at every level, with lengths. Strings are stored as sent; the content rule trims to check. Amounts are strings checked against `MONEY_TEXT`, never JSON numbers (D13).
- **The save** (`settings.service.ts`): one transaction. `SELECT … FOR UPDATE` on the group's row (no `deleted_at` filter, as every settings loader: D20), then update, or insert with `onConflictDoUpdate` on the group for two first saves at once; then one `audit_log` entry, "Changed company profile", "Changed number format", "Changed payments" or "Changed expense approval", with `before` (read under the lock) and `after` as the API answers the section (the number format as the wire list), `null` before a first save. `@Audited()` silences the safety-net entry. The section is replaced whole; the last save wins.
- **Data scope `all` for every settings save** (D4): settings bind the whole company, as the books do (ADR 0040). No default role is affected.
- **The step-up for Payments** (D5): the two-person check and the write-off limit are fraud controls over money in and out, and `settings.payments.manage` is an MFA key. The code is asked after the content checks, on screen and on the API: the page runs `paymentSettingsProblem` before it opens the step-up dialog, and the API runs it before it checks the code. So a refused value never costs one (review round 1). Expense approval has none (its key is not an MFA key; Q1).
- **No control-database write** (D11): `tenants.legal_name` keeps what provisioning wrote (Q5).

### 4. Who reads what (D3, D9)
- `profile` and `numbers`: every member (documents and every `<Num>`). The **EIN** is `""` unless the person holds `settings.company.manage`: only Company profile reads it, and no document prints it.
- `payments`: holders of `sales.invoice.view` or `settings.payments.manage` (the invoice page's payment sheet and Update status, and the Payments page).
- `expenses`: holders of `settings.expenses.manage` (only Settings → Expenses reads it; telling every member the approval line makes it easy to split an expense under it).
- A section is left out when its module is off; payments and expenses also when their product feature (`sales.payments`, `finance.expenses`) is off. Profile and numbers stay answered while their page's switch is off, because the rest of the app uses them; their PUT answers 404 then.
- **Accepted residual:** the audit log's "Changed company profile" rows carry the EIN in `before` and `after`, and holders of `settings.audit.view` read them (Q2).
- No property of the answer is a `SENSITIVE_FIELDS` name, and the interceptor still runs.

### 5. A section never saved (D10)
`GET /settings` answers what the API acts on: the US pack's number format, expense approval off, a blank profile, and payments as "every payment waits, nothing can be written off" (`approvalRequired: true`, threshold `""`, `writeOffMax: "0.00"`, `PAY-`, `RF-`), while the API refuses payments until the row exists (409). `numberSettingsProblem` compares the locale and currency with the US pack then (Q7, Q9).

### 6. The web
- **`API_METHODS`:** `getSettings` reads `GET /settings` first, then lays the served sections over DemoStore's copy (`settingsFromAnswer`: only `API_SETTINGS_SECTIONS` are taken, numbers through `numbersFromWire`; anything else in the answer is ignored, so a newer API never widens an older web). `updateSettings` sends a served section to `PUT /settings/<section>` (numbers as the wire list) and reads again; any other section stays on DemoStore. `getDefaultSettings` and `resetSettings` stay unrouted (D7).
- **The shell follows at once.** The provider's one query reads `GET /company` and `GET /settings` together, and the transport re-reads after every answered write, so a saved number format or profile shows on the saver's own open screens without a reload; another person's screens follow on their next write or load. A refused or failed first read shows GET /company's full-page refusal (it fails closed).
- **Four screen edits** (D16): `saveSection` makes a refused save show its message in a toast and keep the draft, on every settings page, with or without a step-up (it also fixes the silent Currency and Sales tax tabs); Payments gets `stepUp`; `SettingsForm` takes the section's shared rule (`problem`), which Save runs before the step-up dialog or the request (`nextSaveStep`), and Payments and Expense approval pass theirs (review round 1); Company profile builds its rules from the shared patterns and messages.

### 7. DemoStore
`updateSettings` checks, for every section and in the API's order (`permissionDecision` refuses a module that is off before a missing key): the module ("This part of the product is not switched on for your company."), the keys (the role message), the switch ("This feature is switched off."), data scope `all` (`SETTINGS_SCOPE_MESSAGE`; View as limits it), then `settingsSectionProblem`. It can only refuse more than before. Kept different: DemoStore reads every section in full from its own copy; its step-up is the dialog alone (any six digits); its audit `before` and `after` are `diffSummary` text.

### 8. Smaller decisions
- **D6, numbers as a list** in the GET, the PUT body and answer, and the audit entry; stored rows keep `NumberSettings`, which `loadMoneyFormat` reads.
- **D12, the number format keeps the company's own locale and currency** (rule 12: compared with the stored or pack value, no literals).
- **D15, unmoved pages keep saving in the browser** in api mode until their part (Q6).
- **D17, the `auth.step-up` register row** gains Payments (text only; `features.ts` unchanged). `/feature-change` step 2's owner confirmation is replaced by the queue's safest-default rule.
- **D18, payment and refund prefixes must differ**: `refunds` has no unique number index.
- **D21, the Payments threshold is checked even while approval is off.**
- Build-time choices (the session log's B1 to B14): the "server acts on it" API cases run in a provisioned company; a few extra shared messages so every refusal has words; the save takes an `answered` mapper so the locked `before` maps like `after`; A14 holds the row so the lock is pinned.

## Consequences
- **Deploy the API before the web.** `GET /settings` is on the shell's first read and the invoice and quote pages' reads; a web that has it against an API that doesn't (404) or a 5xx there keeps everyone out with the refusal page. An older web against a newer API ignores sections and kinds it doesn't know.
- One more light GET per shell load, per answered write and per invoice or quote page load, beside GET /company's.
- **No schema, migration or dependency change;** nothing in `apps/api/src/core`, packages/providers, packages/db, `features.ts` or the web's session. docs/FEATURES.md changes text only.
- **Changed behaviour in the demo too:** a bare point or a sign in a Payments or Expenses amount, and equal payment and refund prefixes, are refused; a role or View as with a scope narrower than `all` can't save settings; a switched-off section, or one whose module the company lacks (Harbor's payments), refuses; saving Payments asks for a code; every refused settings save shows its message.
- **Residual risks:** unmoved sections still save in the browser only in api mode (Branding, Sales and documents, Localization and tax, Warehouses and showrooms, Shared costs, HR settings, Email, Stock rules, Meetings); the Expenses page is mixed (approval on the API, shared costs in the browser); Reset to default reads DemoStore's fixture originals; the bell's and Outbox's money format is DemoStore's until that task; last save wins within a section (both audited); a screen added later that reads `payments`, `expenses` or the EIN for someone outside the readers gets DemoStore's copy in api mode (add the reader); a new prefix starts numbering at 0001.
- **Tests:** packages/shared `settings-sections.test.ts` (R1 to R11) and `decimal-text.test.ts` (R9); apps/api `settings.int.test.ts` (A0 to A15, 40 cases: metadata against the shared table, the per-person answer and its key walk, never-saved answers, every role in both products, strict bodies, the step-up order, module, ceiling, scope and switch, the server applying the saved payment and expense rules, own company only, one audit entry per save, the row lock, `/settings/accounting` unchanged); apps/web units `settings-answer` (W1 to W7), `save-section` (SF1 to SF3), `demo-settings` (D1 to D8) and two `api-rereads` cases; api-mode e2e `tests/e2e-api/settings.spec.ts` (E1 to E3, which heal and restore Summit's values); demo e2e S1 in `tests/e2e/settings.spec.ts`. 23 mutations of the protections, each caught.

- **Context:** in api mode Sales and documents and all four tabs of Localization and tax saved through `updateSettings("localization")`, which stayed on DemoStore, so they saved in the browser only while the server numbered quotes, invoices and purchase orders, set new customers' terms, dated deposit balances and checked a salesperson's waste from its own `localization` row. A waste default changed in api mode already made every salesperson's new line of that category a 403 (the builder started from DemoStore's copy; `assertWaste` compared with the server's). The section is one record whose rule takes either localization key, so `settings.tax.manage` could save every tab. Part 1's review also asked that `GET /settings`' answer dispatch be exhaustive before any section is added.

### Decision
- **First, an exhaustive dispatch (D19).** `SettingsService.answer` and the web's `settingsFromAnswer` `switch` over the served sections and end in a `default` that throws the shared `unservedSection(section: never)`. Leaving a section of `API_SETTINGS_SECTIONS` out fails the typecheck; a section that gets past the types fails closed (a 500 on the read, an error in the merge) instead of being answered as `expenses` or kept as DemoStore's copy.
- **One key per tab, in both modes (D3).** packages/shared `LOCALIZATION_TABS` gives each tab exactly one key (its type allows one), the `settings.localization` switch, a module and an audit label: Region, Currency and Payroll rules `settings.localization.manage`, Sales tax `settings.tax.manage`, Sales and documents `settings.localization.manage`. Modules: documents `core` (it numbers and prints Flooring's documents, D13), payroll `hr` (the overtime rule drives timesheets and pay, D12), the rest `platform` until their parts.
- **A per-tab ApiClient method (D2).** Screens call `updateLocalization(tab, value)`; `documents-page.tsx` and `localization-page.tsx` change one line each. In api mode the tabs in `API_LOCALIZATION_TABS` (`documents`, `payroll`) are `PUT /settings/localization/<tab>` followed by a read; Region, Currency and Sales tax go to DemoStore's `updateLocalization`, which checks that tab's own key. No client or server diff of the half-DemoStore copy.
- **The routes.** `PUT /settings/localization/documents` and `PUT /settings/localization/payroll`, each with the guard's module then key (from `LOCALIZATION_TABS`), then in the handler: the switch (404), data scope `all` (403), a strict body (400), the shared rule (400), then the save. No step-up (D6): the blueprint asks one only for base currency and tax.
- **The save (D7).** One transaction: `SELECT … FOR UPDATE` on the `localization` row (a private `lockGroup` shared with part 1's `save`), then only `[tab]` is replaced, so the other tabs and the stored tax block stay as they were and `tax_rules` and `tax_jurisdictions` are never touched; one `audit_log` entry, "Changed localization and tax", target the tab's label ("Sales and documents", "Payroll rules"), `before` and `after` that tab only (D5). A company with no `localization` row answers 409 `settings_missing` and nothing is created: a row made from one tab would leave the others `undefined` for `loadLocalization`, the tax context and numbering.
- **The content rules** (`packages/shared/src/settings/localization-rules.ts`, the same words in both modes; D10):
  - the late fee, default deposit and each default waste are the quote API's percent (`PERCENT_TEXT`, at most 100), so a saved default never makes a new quote unsavable and nothing malformed reaches decimal.js (CLAUDE.md rule 6);
  - the default waste covers exactly the waste categories (a missing one would make `assertWaste` refuse every salesperson's line of it);
  - days are whole (quotes valid 1 to 365, balance due 0 to 365); terms are a known payment term;
  - the quote, invoice and purchase order prefixes follow `DOCUMENT_PREFIX_TEXT` (moved here from `section-rules.ts`) and differ without case (D4);
  - none of them starts with the credit notes' `CR-`, in any case (`CREDIT_NOTE_PREFIX`, review round 1). Credit notes are invoices in the one `invoices_number_uidx`, so an invoice prefix of `CR-` gave the next invoice and the next credit note the same number: a 500 on every later credit note, which reverting the prefix couldn't undo because the invoice is posted. As defence in depth the API and the demo now number a credit note from every invoice number, not the notes' alone;
  - the legal footer is at most `LEGAL_FOOTER_MAX` (1,000) characters; the API's outer bound is ten times that, so the shared rule names a long footer in its own order;
  - payroll refuses `overtimeRuleProblem` (California while `hr.payroll.california` is off, ADR 0050) and a holiday state that isn't a US state code.
  Zod checks only types, outer lengths and unknown fields, and each outer length carries its field's shared words; the page's prefix, percent and waste inputs stop at the rule's lengths (`DOCUMENT_PREFIX_MAX`, `PERCENT_TEXT_MAX`), so a person never meets an outer length (review round 1); the input types `DocumentsInput` and `PayrollInput` are what the body check outputs and the rules take, so nothing on the API casts a body (D11). `localizationProblem` runs both tab rules for the screenless whole-section path.
- **Who reads what (D8, D15).** `GET /settings` answers `localization: { documents?, payroll? }` per `LOCALIZATION_READERS` and the tab's module (`readableTabs`, sharing one `isReadable` with part 1's `readableSections`): documents to `sales.quote.view` (the builder's deposit, waste and expiry), `sales.invoice.view` (invoice and receipt footer), `purchasing.order.view` (PO footer) and `settings.localization.manage`; payroll to `hr.timesheet.view` (every default role of a company with HR), `hr.overview.view`, `settings.hr.manage` and `settings.localization.manage`. Neither is hidden by the page switch. Region, Currency and Sales tax are not answered; a company with no row gets no `localization`. The web takes only the served tabs from the answer.
- **DemoStore (D16).** `updateSettings` and the new `updateLocalization` share one `assertSettingsSave` (module, keys, switch, scope; the guard's order, which part 1 already applied), then the tab's rule, and audit the tab's label.

### The B6 interaction
Documents must reach every quote reader, so a builder opened after a change starts new lines from the server's default and the server accepts them from someone without `sales.waste.view`. A builder already open across a change keeps the old default on lines it already holds; a salesperson can't see or change their waste, and `assertWaste` compares each new line with the current default, so every save of that draft is refused ("Your role does not allow changing waste.") until she removes and re-adds those lines or reloads and loses the draft. The lasting fix belongs to the waste rule (the server fills a new line's waste for people without `sales.waste.view`, or the builder re-applies a changed default to unsaved lines still at the old one; owner question Q6 of the session log).

### Consequences
- **Deploy the API before the web.** A web of this part against an API without the routes gets 404 on save, shown in the toast, and nothing is saved anywhere (fails closed); its `GET /settings` without `localization` keeps DemoStore's copy, as before. ### Decision
- **The routes (D2).** `POST /locations` and `PUT /locations/:id` in the inventory module beside `GET /locations`: module `core` (class guard), `settings.locations.manage` from the shared `LOCATION_RULE` (Stock rules' own key, switch and module), then in the handler the `inventory.locations` switch (404), data scope `all` (403, the settings controller's `requireWholeCompany`, now exported: one scope check, D23), the strict body (400); in the service, under the stock lock, not found (404), then the shared rules (400 with their words). No step-up (not an MFA key).
- **`GET /locations` is not switched (D3).** Every module picks a location, so the read stays answered while the switch is off; the switch hides the page and its writes.
- **What editing may do (D4 to D11, D22; spec rule 29, `location-rules.ts`, the same words and order in both modes).** Name trimmed, 1 to 80, unique among live locations as the stock import folds names (D9: `findLocation` takes the first folded match). Address: the company profile's rule, extracted as `streetAddressProblem` (D10). Samples whole 0 to 100,000, showrooms only; floor area blank (stored as none) or `QUANTITY_TEXT` (D11, D23: the inventory controller's quantity pattern, now shared). **The branch is fixed once added** (D5): expense scope reads a location's branch live and quotes take theirs from it on every save; a new location needs a live branch of the company, an unknown one is refused with words. **One default warehouse** (D7): a new default clears the old in the same transaction. **Warehouse to showroom** (D6) only with no stock, no transfer in transit from or to it, no stock held for an invoice (an active reservation above zero; a short row holds nothing and doesn't block, D22) and no open quote shipping from it by header or line. Showroom to warehouse always. **No removal or deactivation** (D4; Q1).
- **The lock (D8).** Every location save takes `lockStock`, so the holds serialize with every stock writer and two saves can't both pass the default or name checks.
- **Bodies (D12).** Strict; outer bounds ten times the rule's maxima with the rule's words; the address with part 1's bounds without words (`ADDRESS_INPUT`, shared with Company profile); the branch checked by membership in JS, never cast in SQL; no id in the body; server UUID v7 ids; the path takes any UUID.
- **Audit (D13).** "Added location" / "Changed location", category `settings`, target the name, before and after as answered; the cleared default gets its own entry; every saved row, a no-op save too.
- **Converting a quote (D21).** `POST /quotes/:id/invoice` refuses, right after it takes the stock lock and before anything is posted or held, a quote whose header or line warehouse is no longer a live warehouse ("Fulfil the quote from a warehouse.", the quote save's words). So no path holds stock for an invoice at a showroom. Taking the stock lock in every quote save was not chosen: it would serialize quoting with every stock change.
- **The web (D14, D15).** `list`/`get("locations")` read `GET /locations`; `saveLocation` sends PUT for a UUID and POST otherwise, never the id in the body. The page names branches from the shell (closing ADR 0051 "GET /company" D7), runs the shared rule before sending, shows the branch read only on an edit, takes the floor area at scale, and its inputs stop at the rule's and the API's lengths.
- **DemoStore (D16).** `assertSettingsSave(LOCATION_RULE)`, the shared rules and holds on its own records, `locationStored`, the cleared default audited (`diffSummary`), the generic `save("locations")` refused.
- **The branch limit stays stored, not enforced (D17):** locations aren't branches, and no branch editor exists.

### Later parts
- **4b:** Shared costs (`PUT /settings/sharedCosts`, `fixedPctProblem` on the server), stacked on 4a, planned in full after 4a's handoff (plan section 17).
- **Not planned without the owner:** retiring a location (Q1, a schema change or a soft-delete design), moving one to another branch (Q2), database-enforced default and names (Q3, indexes). A branch editor brings the branch limit.

### Consequences
- **Deploy the API before the web.** A 4a web against an older API: lists still work (`GET /locations` exists), saves answer 404 in the dialog (fails closed). An older web against this API keeps saving in the browser.
- **The demo refuses more:** module, switch and scope, a branch change, folded duplicate names, the new holds, the generic save of locations.
- **A quote whose warehouse stopped being one** is refused at conversion until its warehouse is changed.
- **Residual risks:** the dashboard's warehouse filter reads the API's locations while its quotes are still DemoStore's, so with a warehouse picked its pending quotes read 0; Shared costs on the Expenses page list the API's locations but still save in the browser until 4b; saved demo data with an empty floor area still breaks the demo Business report until saved again; short rows stay at a location that became a showroom (they hold nothing); quote saves don't take the stock lock (conversion re-checks); a location added in the wrong branch can be renamed but not moved or removed; a company with no branch can't add a location; rows written outside the API (seed, imports) aren't re-validated until a save touches them.
- **No schema, migration or dependency change;** nothing in `apps/api/src/core`, auth, tenancy, packages/providers, packages/db, the control database or `features.ts`. docs/FEATURES.md changes text only.
- **Tests:** packages/shared `location-rules.test.ts` (LNR1 to LNR14); apps/api `settings-locations.int.test.ts` (LNA0 to LNA18, 31 cases, its own provisioned companies); apps/web units `locations-api` (LNW1, LNW2), `demo-locations` (LND1 to LND6), `location-form` (LNP1 to LNP3) and one `api-rereads` case; api-mode e2e `tests/e2e-api/settings-locations.spec.ts` (LNE1, LNE2, which heal Southgate Showroom by street and put it and Colorado Springs back) and `company.spec.ts`'s exact Branch check; demo e2e LNS1 and LNS2 in `tests/e2e/warehouses.spec.ts`. 35 mutations of the protections (LNM1 to LNM35), each caught.
