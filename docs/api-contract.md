# API contract

Every screen reads and writes data through the `ApiClient` interface in `apps/web/src/lib/api/contract.ts` (CLAUDE.md rule 1). The demo implementation is `DemoStore` (`apps/web/src/lib/api/demo/`): generated fixtures moved to today's date, plus a per-company localStorage overlay. `NEXT_PUBLIC_DATA_SOURCE=demo` selects it. To connect the real API, write an HTTP client that implements the same interface and select it in `apps/web/src/lib/api/index.ts`. Screens do not change.

The tenant always comes from the session, never from a parameter, as it will on the real server. The suggested REST endpoints below are what the real client would call.

## Conventions for apps/api (real build, decided 2026-11-12)

- **Moving a module.** With `NEXT_PUBLIC_DATA_SOURCE=api`, `apps/web/src/lib/api/index.ts` routes each `ApiClient` method listed in `API_METHODS` (`lib/api/http/api-methods.ts`) to apps/api through `HttpTransport`. Every other method stays on DemoStore. A module's pull request adds its methods there. The persona picker and `/api/demo/*` exist only in demo mode.
- **URLs.** No version prefix. Resources are plural and kebab-case (`/purchase-orders`, `/supplier-payments`). `GET /:resource` lists and `GET /:resource/:id` reads. A business action is `POST /:resource/:id/<action>` (`/invoices/:id/void`), never a PATCH of a status field. `/me/...` is the signed-in person's own data.
- **Tenant.** It comes only from the verified session, never from a path, query or body. The API picks the company database through `TenantConnectionService` (P9).
- **Bodies.** JSON with camelCase fields. Every body is checked with a Zod schema from `packages/shared`. Money, quantities and rates are decimal strings, never JSON numbers. Their text is not canonical: the same amount may arrive as `"0"`, `"0.00"` or `"0.000"` (a numeric(14,3) column keeps its scale), so clients compare them by value with decimal.js, never as text (STATUS B3). A write takes back the percents the API answers at numeric(18,8) scale (`"50.00000000"`): a quote's deposit and waste and a contract's retainage with up to four decimals by value, a commission share with up to two, and the places past them may only be zeros. The quote's waste check compares waste by value, never as text (`sameOptionalDecimal`; ADR 0037, 2026-11-17). Not every change check does: the quote's `taxOverride` is compared as text, so a client sends back the override it was answered, unchanged. Amounts in settings (the payment and expense approval thresholds, the write-off limit) are `MONEY_TEXT` strings (digits with up to two decimals, no sign, exponent or bare point) or empty, stored as sent; the number format's decimals travel as a list of `{ kind, places }`, because `unitCost` is a reserved sensitive name (ADR 0059). Area is in sq ft and length in ft. Dates are `YYYY-MM-DD` and moments are ISO 8601 in UTC.
- **Errors.** Every failure returns `{ code, message, details? }`. `message` is written for the person and shown as it is.

  | Status | Code | When |
  | --- | --- | --- |
  | 400 | `invalid_request` | The body failed validation |
  | 401 | `unauthenticated` | No valid session |
  | 403 | `forbidden` | Product, module, permission or data scope says no |
  | 404 | `not_found` | Also used for records outside the caller's data scope, so their existence does not leak |
  | 409 | `conflict` | State changed underneath, or a duplicate |
  | 422 | `rule_broken` | A business rule refused |
  | 429 | `rate_limited` | Too many requests |
  | 500 | `internal_error` | Unexpected; details are logged on the server only |

  The web client turns all of these into `ApiError`, so screens handle them as they handle a DemoStore rule error.
- **Re-reading after a write.** In api mode the HTTP transport tells the screens to read again after every non-GET request the server answered, a success or a 400, 403, 404, 409 or 422 refusal, once the response is OK or refused and before its body is parsed. A GET never does, and neither do a network failure, 401, 429 or 5xx. A POST that only reads goes through `requestAsRead` and never re-reads: `POST /auth/step-up`, `POST /imports/check`, `POST /pay-periods` (it runs inside a read) and the timesheet upload's dry run. A method factory can't re-read on its own (ADR 0051, 2026-11-16).
- **Lists.** Filtered by data scope on the server. Pagination arrives when a module needs it, as `?limit=&cursor=` returning `{ items, nextCursor }`.
- **Sensitive fields.** Cost, margin, pay rate and credit limit are removed by the server without `view_sensitive`. Hiding them on screen is not enough (sales.md, inventory.md). A client treats a field the server left out as unknown, never as zero: no margin without cost (`computeTotals`, `monthlyPnl`, `salesTotals`, `bestSellersIn`, `teamStats`; ADR 0037, 2026-11-16 and 2026-11-17).
- **Uploads.** Files go to storage through a signed URL from the StorageProvider. The API stores an `attachments` row and checks the real file type.
- **Docs.** OpenAPI is generated from the controllers at `/docs` (browsable) and `/docs/openapi.json`. `GET /health` is public.

## Authentication (real build, P8, ADR 0029)

In api mode the browser reaches these through the web app's own origin: Next.js rewrites `/api/auth/*` to apps/api's `/api/auth/*` and `/api-proxy/*` to the rest of apps/api, so the session cookie (`better-auth.session_token`, httpOnly, SameSite=Lax, `__Secure-` in production) is first-party on each product host. Better Auth's endpoints answer with Better Auth's own error body, `{ code, message }`, whose codes are upper case, such as `INVALID_EMAIL_OR_PASSWORD`.

**Web screens (ADR 0060).** The ApiClient's `signInSecurity`, `confirmPassword`, `addPasskey`, `renamePasskey` and `deletePasskey` call `GET /auth/context` and the endpoints above under `/api/auth` (never `/api-proxy`, which refuses auth paths). `confirmPassword` is sent as a read; adding, renaming and removing re-read like any write. The login page's passkey sign-in calls `generate-authenticate-options` and `verify-authentication` directly.

**Mandatory MFA (blueprint p27).** Owner, Accountant, HR and active platform admins must use a second factor. Until they have one, their session may only set up an authenticator app or a passkey, read `/auth/context`, choose a company and sign out. Every other Better Auth endpoint and every guarded route answers 403 `mfa_enrolment_required`. The roles are read from `member.role`, which holds the person's company role keys, comma-separated.

**Auth only through the web host.** With `AUTH_PROXY_SECRET` set (required in production), any `/api/auth/*` request that does not carry the web proxy's secret answers 403 `proxy_required`. The web host answers 404 for `/api-proxy/api/auth/*`.

## Tenancy (real build, P9, ADR 0030)

Every Nest route needs a signed-in session with an open company, unless it is marked `@Public()` (`GET /health`, `GET /public/branding`) or `@SessionOnly()`. The session-only routes are `GET /auth/context` and `POST /auth/step-up` (ADR 0034), the seventeen /platform routes (ADR 0052, ADR 0053 and ADR 0056), which carry `PlatformAdminGuard` at class level as their only authorization layer, and `GET /company/standing` (ADR 0054), which carries `StandingMemberGuard` at class level. That guard repeats TenantGuard's membership checks on control rows only, with TenantGuard's codes and words in TenantGuard's order (`company_required`, `not_a_member`, `product_not_enabled`), takes the company from the verified session, and never builds a TenantContext or opens the company database (see "Company standing and billing"). The guards run globally in this order: SessionGuard, then TenantGuard. So a new route is closed until it says otherwise.

The company always comes from the verified session. A `companyId` or `tenantId` in the path, query, body or headers is never read. Company data is reached only through `TenantConnectionService.db(tenant)`, where `tenant` is the `@CurrentTenant()` context that TenantGuard made.

**The one exception: platform routes (ADR 0052).** A /platform route names the company it acts on, by `:id` (a UUID, checked with `ParseUUIDPipe`), or by `companyId` in the support request's body and in the query of `GET /platform/audit` and `GET /platform/support-grants` (a UUID, "That company id is not valid." otherwise). That id selects control-database rows only: `tenants`, products, subscriptions, module overrides, the ceiling, branding, database status and member counts. It is never passed to TenantConnectionService, no TenantContext is built from it, and no company database is opened, so CLAUDE.md rule 2 holds. Lint bans the tenancy, tenant-context and company-schema imports in `apps/api/src/modules/platform`, and a test shows these routes answering for a company whose database failed or is in maintenance.

| Status and code | When |
| --- | --- |
| 401 `unauthenticated` | No session, or a host Better Auth does not serve |
| 403 `company_required` | The session has no open company (the chooser), or the company is deleted |
| 403 `not_a_member` | The person was removed from the company during the session |
| 403 `product_not_enabled` | The company lacks the product the web host serves (`x-demo-product`), or one the route requires with `@RequireProduct()` |
| 403 `company_read_only` | A write (anything but GET, HEAD or OPTIONS) to a company in a read-only period (suspended, cancelled, or a lapsed plan; ADR 0033) or whose database is read-only. Reading still works (blueprint p29, p40) |
| 403 `company_suspended` | The company's read-only period is over, so it is locked. Sign-in and `/auth/context` still work, and no data is deleted (ADR 0033) |
| 503 `company_maintenance` | The company is under maintenance (a move or a failed migration): no reads or writes (ADR 0033) |
| 503 `company_unavailable` | The company database is not ready (provisioning, migrating or failed) |

## Permissions, sensitive fields and audit (real build, P10, ADR 0031)

Every company route declares what it needs: `@RequirePermission(...keys)` (any one key from the packages/shared catalog), optionally `@RequireModule(module)`, or `@AnyCompanyMember()` for a person's own information. Three `@AnyCompanyMember()` routes answer more than that: `GET /locations` (shared reference data), `GET /company` (the company's reference data and a names directory, ADR 0051 "GET /company") and `GET /settings` (the company's settings, cut per person, ADR 0059). Effective permissions are role permissions ∩ the company ceiling ∩ enabled modules, worked out by the shared engine on every request.

| Status and code | When |
| --- | --- |
| 403 `forbidden` | The person holds none of the route's keys, or their profile in the company is disabled. Message: "Your role does not allow this. Ask an Owner to change your security role." |
| 403 `module_not_enabled` | The route's module is not on for the company (not in its products or plan, or switched off) |
| 403 `permission_undeclared` | The route declares no permission. This is a bug in the route, refused so it fails closed |

**Sensitive fields.** A company response, and the `details` of a company error, never contains a field listed in `SENSITIVE_FIELDS` (packages/shared) unless the viewer holds the key that reveals it. The list covers product cost, margins, job costing, pay rates, credit limit and contract line estimated cost; ADR 0031 lists every name. The server removes them at any depth, in camelCase or snake_case. These property names are reserved for sensitive values, and job costing uses `jobCost`, `jobMargin` and `jobMarginPct`.

**Audit.** Every successful company write (POST, PUT, PATCH, DELETE) writes an `audit_log` entry: the module's own, with before and after, or the API's safety-net entry (category `data`, the route and the record id). The log is append-only: the database refuses UPDATE, DELETE and TRUNCATE.

## Platform admin (real build, ADR 0052, ADR 0053 and ADR 0056)

Parts 1 (ADR 0052), 3 (ADR 0053) and 2 (ADR 0056). Spec: docs/specs/platform-admin.md (draft). Every route is `@SessionOnly()`: it needs a session but no open company and never uses the open company. TenantGuard, PermissionGuard and the AuditInterceptor don't apply, so `PlatformAdminGuard`, set at class level, is the only authorization layer. It runs in this order:

1. No verified session: 401 `unauthenticated` (SessionGuard answers first; the guard is the backstop).
2. `admin.access` off: 404 `not_found`, on every route below. A route that names its own switch with `@PlatformFeature(key)` (the plans and company status routes name `admin.billing`) also answers 404 while that switch is off. Both are read on every request, before the admin row is read.
3. Not a platform admin: 403 `forbidden`, "Only platform admins can use this.". An admin has a `platform_admins` row that is `active`, not deleted, with role `owner` or `support`; any other role counts as none. The row is read on every request.
4. A write (not GET, HEAD or OPTIONS): the `owner` role unless the route allows `support` (403 "Only the platform owner role can change this."), then a step-up from the last 5 minutes (403 `step_up_required`, or `step_up_mfa_required`).

SessionGuard's own refusals come first: an admin with no factor gets 403 `mfa_enrolment_required`. Guards run before pipes and the body check, so a non-admin gets 403 whatever the body. `:id` is a UUID (400 `invalid_request` otherwise) and names control-database rows only (see Tenancy). An unknown or deleted company is 404 "That company does not exist.".

**Change company access.** `accessPatchProblem` (packages/shared, also run by the demo store) refuses with 400 `invalid_request`:
- a `modules` list without `platform`: "The Platform module can't be switched off.";
- a module the company's products don't offer, or a hidden one (rule 18): "The {label} module isn't offered to this company.";
- a key not in the catalog: "{key} is not a permission."; a key whose module is not offered and visible: "{key} is outside this company's products.";
- a `ceiling` list without all of `settings.users.view`, `settings.users.manage`, `settings.roles.view`, `settings.roles.manage` and `settings.audit.view`: "A company always keeps the Users, Security roles and Audit log permissions, so it can manage its own people.";
- a limit that is not a whole number from 1 to 100,000: "Enter a whole number from 1 to 100,000.".

A limit for a company with no subscription row that is not deleted is 422 `rule_broken`, "This company has no plan, so it has no limits to change." (`ACCESS_NO_PLAN_MESSAGE`; it said "trial" before ADR 0053); no row is ever created.

A save is one control transaction that locks the company row first:
- **modules:** an override row only where the choice differs from the plan, `deleted_at` cleared; a stored override for a module set back to the plan is soft-deleted. Hidden modules and `platform` keep their rows;
- **ceiling:** only the rows whose `allowed` value changes;
- **limits:** the override columns of every subscription row that is not deleted, cancelled ones included, null where the row's plan already gives the number;
- **audit:** one `company.access_changed` row in `platform_audit_log` (actor, company, IP, user agent; `before` and `after` hold the changed modules, keys and limits, plus `overrideRows` and `limitRows` when rows were written), or none when nothing was written. Nothing goes to the company's own `audit_log`.

Guards read modules, the ceiling and limits on every request, so a change applies to the company's next request: 403 for a removed key, `module_not_enabled` for a module switched off, `seat_limit` on the next invitation. Reads are not audited.

**Platform audit (`GET /platform/audit`, ADR 0053).** Query, strict (an unknown or repeated parameter is 400 `invalid_request`):
- `companyId`: a UUID, "That company id is not valid.". No existence check, so a deleted company's history still lists;
- `action`: one of `company.access_changed`, `support.requested`, `support.approved`, `support.revoked`, `company.migration_failed`, `company.migration_recovered`, and since ADR 0056 `company.suspended`, `company.reinstated`, `company.cancelled`, `plan.created`, `plan.changed`, `plan.retired`, `plan.restored` (13 in all), "Choose an action from the list.". While `admin.billing` is off the last seven are refused with the same message (`platformAuditActionOn`, read on every request); their rows still list unfiltered;
- `before`: the `id` of the last entry of the previous page; a UUID that names an existing entry, "That page of the audit log does not exist. Start from the newest entries.";
- `limit`: digits, 1 to 100, default 50, "Ask for 1 to 100 entries at a time.".

Order `at desc, id desc`; the cursor is compared in SQL as `(at, id)`, so entries of the same millisecond page correctly under any filter. `nextCursor` is the last entry's id while there are more, else null. Each `PlatformAuditView` is `{ id, at, action, company { id, name } | null, actor, targetType, targetId, details, network? }`:
- **`actor`** comes from the action, never from today's `platform_admins` rows: `{ kind: "platform_admin", userId, name }` ("Former admin" when the user row is gone) for the access save, the support request and, since ADR 0056, the plan and status actions; `{ kind: "company_user" }`, with no id or name, for the Owner's approve and revoke; `{ kind: "system" }` for migrate.ts; `{ kind: "unknown" }` otherwise;
- **`details`** is a per-action allow-list in packages/shared (`platformAuditDetails`), deny by default: `access_changed` (the four lists, `userLimit` and `branchLimit` as `{ from, to }`, and `overrideRows` and `limitRows` as counts); `support_requested` (`reason`, `expiresAt`); `support_decided` (`decision`); `migration_failed` (`code` only, for every row, old ones included); `migration_recovered` (`version`); since ADR 0056 `status_changed` (`from`, `to`, `reason`), `plan_created` (the plan's nine fields and `reason`), `plan_changed` (`changes` as `{ field, from, to }[]`, and `reason`) and `plan_active` (`active`, `reason`); and `{ kind: "hidden" }` for anything that doesn't fit its shape exactly;
- **`network`** (`{ ip, userAgent }`) only for the owner role, and only on platform admins' own entries; the key is absent otherwise, and for the support role the columns are never selected;
- **the support role** gets another admin's `support.requested` entry with `details: { kind: "hidden" }`, its actor and company kept, and another admin's plan or status entry with `reason: null` ("Reason hidden"): `after.reason` is set to null in SQL (`jsonb_set`, only when `after` is an object; any other `after` is dropped) and by the shared view again. The owner role reads every reason, and an admin always reads its own;
- `action`, `targetType` and `targetId` show only when they match their patterns (`targetId` a UUID), else `"unknown"` or null.

Migration text, other admins' reasons and company people's ids and names are narrowed out in SQL before the shared mapping checks every row again. Reading writes no audit row. There is no export.

**Support requests (ADR 0053).** The POST runs in one control transaction: it locks the admin's own `platform_admins` row (`FOR UPDATE`) and re-checks it (403 "Only platform admins can use this."), then checks the company (404), then refuses an open grant (pending or approved, unexpired) by the same admin for the same company with 409 `grant_open`, "You already have an open support request for this company.", then 10 requests by the admin in the last 24 hours, across companies and counting revoked, expired and deleted grants, with 429 `rate_limited`, "You can send at most 10 support requests in 24 hours. Try again later.". A refused request writes nothing and does not count. The body's messages are "Give a reason of 10 to 500 characters." and "Enter a whole number of hours from 1 to 72.". The status in both lists is derived, revoked first, then expired (`expiresAt` at or before now), approved and pending.

**Plans (ADR 0056).** Prices are data: nothing is charged from them. `PlatformPlan` is `{ id, key, name, product, monthlyPrice, yearlyPrice, modules, maxUsers, maxBranches, active, companies, createdAt, updatedAt }`: prices are decimal strings with two decimals (`"0.00"`); `modules` are the stored ones in catalog order without `platform`, a stored hidden one included; `maxUsers` and `maxBranches` are null only for a plan with no live limits row (no limit; only possible by SQL); `companies` counts the companies with any subscription row naming the plan, deleted rows included, and above 0 means in use. No subscription, company id or company name is returned. A plan whose product is neither `flooring` nor `hr` is left out.
- **`PlatformPlanInput`** `{ key, name, product, monthlyPrice, yearlyPrice, modules, maxUsers, maxBranches, reason }`, every field required; **`PlatformPlanPatch`** `{ name?, monthlyPrice?, yearlyPrice?, modules?, maxUsers?, maxBranches?, reason }`. The schemas check shapes only (strings, numbers, lengths), each with its field's message; then the shared `planProblem` or `planPatchProblem` decides.
- **Refusals, in order** (every write is one control transaction; a refusal writes nothing): the body's shape, 400 `invalid_request`; the acting admin, checked again under a `FOR UPDATE` lock on their own `platform_admins` row, 403 `forbidden` ("Only platform admins can use this." or "Only the platform owner role can change this."); on edit, retire and restore, the plan row locked, 404 `not_found` "That plan does not exist." (a non-UUID id is 400); the field rules, 400; then 409 `conflict` or 422 `rule_broken`.
- **Messages (400):** key "Enter a key of 2 to 40 lowercase letters, digits and dashes that starts with a letter, such as flooring-pro."; name "Enter a name of 1 to 80 characters."; product (also a product row that is missing or deleted) "Choose Flooring Suite or HR Suite."; prices "Enter a monthly price such as 49.00: digits with up to two decimals." and "Enter a yearly price such as 490.00: digits with up to two decimals."; modules "Choose the plan's modules.", "Choose at least one module besides Platform.", "{key} is not a module.", "The {label} module isn't offered with {product label}."; limits "Enter a whole number from 1 to 100,000." (also when only one limit is sent for a plan with no limits row); reason "Give a reason of 10 to 500 characters."; on PATCH, `key`, `product` or any other field "Only a plan's name, prices, modules and limits can change.".
- **Create:** 409 `conflict` "A plan with this key already exists. A key can't be reused, even after its plan is retired." for any taken key, a retired or deleted plan's included (`insert … on conflict do nothing`, so a parallel create of the same key gets the same 409). Writes the plan, one `plan_modules` row per module (never `platform`) and one `plan_limits` row, each with `created_by`, and one `plan.created` row with no company.
- **Edit:** a plan in use whose modules (compared as sets) or either limit would really change: 422 `rule_broken` "This plan is in use, so its modules and limits can't change. Change one company's access on its Access page instead.". Name and prices may always change: a rename shows on every such company's billing page; a price changes nothing any company pays, since each company's price is on its own subscription row. A removed module's row is soft-deleted and a re-added one restored; a stored module the console doesn't offer is kept. A save that changes nothing answers 200 and writes nothing. Two edits of one plan run one after the other; the last one wins and both are audited.
- **Retire and restore:** the reason, then 409 `conflict` "This plan is already retired." or "This plan isn't retired.". Nothing reads `active` for access, so no company changes. No route deletes a plan.

**Company status (ADR 0056).** `PlatformCompanyStatus` is `{ companyId, status, statusChangedAt, phase, readOnlyFrom, lockedFrom, actions }`; `status` is the stored text, even one the console doesn't know (which previews as `locked`); `actions` is always suspend, reinstate, cancel, each `{ action, refusal: { code, message } | null, next: { status, phase, readOnlyFrom, lockedFrom } | null }`, worked out by the shared `statusAfter` from every subscription row, deleted ones included, at the database's time. The preview reads in one read-only, repeatable-read transaction. An unknown or deleted company is 404 "That company does not exist.".
- **Refusals of an action, in order** (each writes nothing): the guard's (401, 404 while `admin.access` or `admin.billing` is off, 403, then 403 for the support role and `step_up_required`); 400 `invalid_request` for the shape, `expectedStatus` missing, empty, over 40 characters or not a string ("Read the company's status again before changing it."), then the reason; 403 under the lock on the admin's own row; 404 for the company, read under `FOR UPDATE`; cancel only, 400 "Type the company's name exactly to confirm." (trimmed, case-sensitive); 409 `conflict` "This company's status changed meanwhile. Read it again." when the stored status isn't `expectedStatus` or another change won the race; then `statusAfter`.
- **`statusAfter`:** 422 `rule_broken` "This company's status isn't one the console knows, so it can't be changed here." for a stored status outside `trial`, `active`, `past_due`, `suspended`, `cancelled`; 409 `conflict` "This company is already suspended.", "A cancelled company can't be suspended. Reinstate it first if it should be suspended instead.", "This company isn't suspended or cancelled, so there is nothing to reinstate." or "This company is already cancelled."; 422 for a company that never had a subscription row (suspend and cancel: "This company has never had a plan. Suspending or cancelling it would also switch off every module but Platform, so its people couldn't read or export their data. To limit it now, switch its modules off on its Access page. This waits for the owner's decision."; reinstate: "This company has never had a plan, so the console can't tell what to put back. This waits for the owner's decision."); 422 "That would give this company more time before it becomes read only or locked than it has now, so nothing was changed." for a suspend or cancel that would widen. Otherwise suspend writes `suspended`, cancel `cancelled`, and reinstate `active` when the company ever paid, else `trial`; `past_due` is never written.
- **What an action changes:** only `tenants.status` (the trigger stamps `status_changed_at` with the transaction's time) and `updated_at`, plus one `platform_audit_log` row with `before { status, statusChangedAt }` and `after { status, statusChangedAt, reason }`. No subscription row, override, ceiling, product, member, session or database row changes; no company database is opened and the company's own `audit_log` isn't written. Cancel deletes nothing, and reinstate undoes it. TenantGuard reads the new status on the company's next request: suspended or cancelled is read only at once (a write gets 403 `company_read_only`), then locked (403 `company_suspended`) as ADR 0033's ladder says; part 4's standing and the Owner's notice read it the same way.

**Not on the API yet:** using a support grant, the company's own roles and users, and billing writes: creating or changing a subscription, recording a payment, correcting a period and invoices (ADR 0052, "For the owner" 7; ADR 0056). The company's own read-only side, standing and the Owner's billing, is in "Company standing and billing (real build, ADR 0054)". The import and database calls below stay on DemoStore; their /admin pages are not found in api mode.

## Company standing and billing (real build, ADR 0054)

Platform admin part 4, the company side. Spec: docs/specs/platform-admin.md, "Part 4: the company side" (draft). Neither route takes a company id: the company is always the verified session's, and a `companyId` or `tenantId` in the query or headers is ignored. Both live in `apps/api/src/modules/billing`, which lint keeps off the company schema and TenantConnectionService; the standing files may not import TenantContext either.

| Route | Access | Who | Answer |
| --- | --- | --- | --- |
| `GET /company/standing` | `@SessionOnly()`, `StandingMemberGuard` at class level | Any member of the session's company, a disabled one included | `CompanyStanding` `{ state }`, `Cache-Control: no-store`. Not audited, no feature switch |
| `GET /billing` | A company route: TenantGuard and PermissionGuard (`@AnyCompanyMember()`), then `settings.billing`, then the Owner | The Owner | `CompanyBilling`, `Cache-Control: no-store`. Not audited |

**Refusals.** SessionGuard first on both: 401 `unauthenticated`, "Sign in to continue." (or `session_expired`), and 403 `mfa_enrolment_required`, "Set up two-step sign-in to continue.".

| Status and code | `GET /company/standing` (`StandingMemberGuard`) | `GET /billing` |
| --- | --- | --- |
| 403 `company_required`, "Choose a company to continue." | No open company, or it is unknown or deleted | The same (TenantGuard), and a company deleted after the guard ran |
| 403 `not_a_member`, "You are no longer a member of this company. Sign in again." | The membership was removed | The same (TenantGuard) |
| 403 `product_not_enabled`, "Your company does not have this product." | The host's product header names a product the company lacks; no header skips the check | The same (TenantGuard) |
| 503 `company_maintenance`, 503 `company_unavailable`, 403 `company_suspended` | Never: these are answered as a state | TenantGuard, before the handler. A read-only company may read |
| 403 `forbidden`, "Your role does not allow this. Ask an Owner to change your security role." | Never | A disabled person (PermissionGuard) |
| 404 `not_found`, "Not Found" | Never | `settings.billing` off, for everyone, the Owner included, before the Owner check |
| 403 `forbidden`, "Only an Owner can see billing." | Never | Anyone but the Owner (`BILLING_OWNER_ONLY_MESSAGE`) |

Only the 200 answers carry `Cache-Control: no-store`; a refusal holds no company data.

**`CompanyStanding`** is `{ state }`, one of five words, the same for every member: what TenantGuard does to the member's next company request, in TenantGuard's order (shared `companyStandingState`).

| `state` | When (control rows only) | What TenantGuard does to a company route |
| --- | --- | --- |
| `maintenance` | Maintenance mode on, whatever else | 503 `company_maintenance` |
| `unavailable` | The database is provisioning, migrating or failed, or there is no database row | 503 `company_unavailable` |
| `locked` | Past the binding ladder's read-only window (ADR 0033) | 403 `company_suspended` |
| `read_only` | In a read-only window (suspended, cancelled, a lapsed plan or an ended trial), or the database is `read_only` | Reads pass; a write gets 403 `company_read_only` |
| `full` | Otherwise | Reads and writes pass |

It never says why (no billing reason, date, plan, status word or maintenance reason) and has no Owner flag. A database row that is `ready` reads `full` even when the database can't be reached; company routes then fail with their own errors.

**`CompanyBilling`** is `{ status, phase, subscriptions, limits, notice }`:
- `status`: `tenants.status` as stored; `phase`: `full` or `read_only` (`companyPhase`, as TenantDirectory reads it; a locked company never reaches the route);
- `subscriptions`: the live subscription rows, oldest first, each `{ planName, product, interval, currentPeriodStart, currentPeriodEnd, standing }`, with ISO moments and `standing` one of `current`, `overdue`, `past_due`, `trial`, `trial_ended`, `cancelled` or `unknown`. `[]` for a fresh trial and when every row is deleted;
- `limits`: `{ userLimit, branchLimit }`, as `PlanLimits` works them out; null is no limit, and the branch limit is stored, not enforced;
- `notice`: null, `{ kind: "payment_overdue", since, readOnlyFrom }` (from the first overdue day of the 14-day grace, or while past due), or `{ kind: "read_only", reason, since, lockedFrom }` with `reason` one of `suspended`, `cancelled`, `payment_lapsed`, `trial_ended`, `database` or `account`. Dates are ISO moments or null, found from `companyPhase` itself (`phaseDates`).

**Never returned:** a price, a subscription id, a plan key, `userLimitOverride` or `branchLimitOverride`, a user id, seats in use or payment details. The row type the view is built from has no price.

**Support access** stays on the routes in "Users, roles, step-up, invitations and support access", unchanged. The Owner's panel in Settings → Users lists, approves (step-up) and revokes; while standing is `read_only` it shows no actions, because TenantGuard refuses both writes then.

## Company and the shell (real build, ADR 0051 "GET /company")

The web shell's person, roles, access, modules and branches. Spec: docs/product-spec/settings-and-permissions.md, Real build, "The shell on the API". The route takes no company id: the company is the verified session's, and a `companyId` or `tenantId` in the path, query, body or headers is never read.

| Route | Access | Who | Answer |
| --- | --- | --- | --- |
| `GET /company` | A company route: SessionGuard, TenantGuard and PermissionGuard (`@AnyCompanyMember()`); no module and no feature switch | Any member whose profile is active | `CompanyAnswer`, `Cache-Control: no-store`. Not audited |

**`CompanyAnswer`** (`packages/shared/src/platform/company-answer.ts`) is `{ company, me, roles, access, people }`:
- `company`: `{ id, slug, name, city, state, timeZone, modules, ceiling, branches }`. `id` is the session's tenant id; `timeZone` is `tenants.time_zone`, the zone the API's own date checks use (`GET /settings`' `localization.region.timeZone` is the same value; ADR 0059, part 2b); `modules` are the enabled modules; `branches` are the live ones by name, each `{ id, name, city, state }`. `ceiling` is the company's permission ceiling, sorted, only for someone holding `settings.roles.view`, `settings.roles.manage`, `settings.users.view` or `settings.users.manage` (`seesCeiling`); `null` for everyone else;
- `me`: the caller's own `User`, exactly as `GET /users` shapes it;
- `roles`: only the roles the caller holds, as `GET /roles` shapes them;
- `access`: `{ permissions, dataScope, isOwner }`, PermissionGuard's own effective access for this request (keys sorted), never worked out a second time;
- `people`: `{ id, name, status }` for every live profile with an account, by name. Everyone gets active colleagues; disabled ones (`status` `disabled`) only holders of `settings.users.view` or `settings.users.manage` (`seesDisabledPeople`; ADR 0051, "2026-11-20"). Invited people are left out.

**Refusals** are the guards' own: 401 `unauthenticated` or `session_expired`; 403 `mfa_enrolment_required` (SessionGuard, or PermissionGuard for a role that needs a factor not yet set up); TenantGuard's 403 `company_required`, `not_a_member`, `product_not_enabled` and `company_suspended`, and 503 `company_maintenance` and `company_unavailable`; 403 `forbidden`, "Your role does not allow this. Ask an Owner to change your security role.", for a disabled profile, and for a profile with no account. A read-only company still answers.

**Never returned:** another company's anything; another person's email, title, roles, branch, MFA, sign-in time, employee link or default warehouse; a role the caller doesn't hold; the ceiling without one of the four keys; billing facts (plan, status, limits; `GET /billing` keeps them); feature switches (the same build on both sides); any `SENSITIVE_FIELDS` name.

**The web:**
- `getWorkspace()` reads it and drops keys and modules the web doesn't know (fail closed). The shell lays its name, place, modules, ceiling and branches over `getCompany()`, which still holds the plan, status, limits and product, and uses its access as is.
- `list("users")` and `get("users")` give its people (id, name and status filled; every other field empty); `whoAmI()` is `GET /auth/context`'s `user.id`.
- View as and Your profile are not offered in api mode.
- A refused first read shows a full page: the company-unavailable panel for a standing refusal, otherwise "Your workspace could not open" with the API's words, each with Try again and Sign out.

## Settings, part 2a (real build, ADR 0059, 2026-11-17)

Sales and documents and the Payroll rules tab of Localization and tax, one tab at a time. Spec: docs/product-spec/settings-and-permissions.md, Real build, "Settings on the API, part 2a". The company is the verified session's. No control-database read or write.

| Route | Access | Handler checks, in order | Answer |
| --- | --- | --- | --- |
| `PUT /settings/localization/documents` | module `core` (checked first), then `settings.localization.manage` | switch `settings.localization` (404), data scope `all` (403), strict body (400), `documentsProblem` (400) | the saved tab (`DocumentsInput`). Audited |
| `PUT /settings/localization/payroll` | module `hr` (checked first), then `settings.localization.manage` | switch `settings.localization` (404), data scope `all` (403), strict body (400), `payrollProblem` (400) | the saved tab (`PayrollInput`). Audited |

- **One key per tab.** Keys, module, switch and audit label come from `LOCALIZATION_TABS` (packages/shared); a tab never takes the section's any-of keys, so `settings.tax.manage` alone saves neither; the whole section is refused in both modes (part 3b). - **Bodies.** Exactly the tab's fields; an unknown field is 400. Then the tab's rule answers its first problem, with the words and in the order the demo uses. The page's inputs stop at the rule's own lengths (`DOCUMENT_PREFIX_MAX`, `PERCENT_TEXT_MAX`), so from the screen both modes name the same problem; only a direct caller that sends a string past an outer length together with another problem can get a different field named.

## Settings, part 3a: Sales tax (real build, ADR 0059, 2026-11-17)

The Sales tax tab of Localization and tax, on part 2b's pattern, with versioned rule and county-rate rows. Spec: docs/product-spec/settings-and-permissions.md, Real build, "Settings on the API, part 3a". The company is the verified session's. The control database is read (the company's day, from `tenants.time_zone`), never written.

| Route | Access | Handler checks, in order | Answer |
| --- | --- | --- | --- |
| `PUT /settings/localization/tax` | `settings.tax.manage` (an MFA key; module `platform`: no module guard) | switch `settings.localization` (404), data scope `all` (403), strict body (400); then under the `localization` row's lock: no row or no tax block (409 `settings_missing`), `taxProblem` against the tab in force (400), then always a step-up (403 `step_up_required`, or `step_up_mfa_required` without a factor) | the tab now in force, read back (the same shape as `GET /settings`' `localization.tax`). Audited |

- **Keys, switch and label** come from `LOCALIZATION_TABS`: `settings.localization.manage` alone can't save Sales tax, and `settings.tax.manage` alone saves only Sales tax. The guards' refusals are part 1's.
- **The body** is exactly `{ pricesInclude, rounding, rules, jurisdictions, companyDefault, filing, certificateTypes }`:
  - `rules`: `{ state, jurisdiction, ratePct, taxable: { material, labor, freight, service }, lumpSumLaborTaxable, validFrom, validTo?, version, rationale }[]`, at most one per US state;
  - `jurisdictions`: `{ id, state, county, name, ratePct, validFrom, validTo }[]`, at most 200;

  - `filing` (`{ state, frequency }[]`) and `certificateTypes` (`string[]`) are required and must equal the stored ones: the tab doesn't change them.
  Every rate is a string `TAX_RATE_TEXT` takes (0 to 99.9999 by value: up to two whole digits and four decimals, then only zeros up to eight, so the answer's `"8.81000000"` can be sent back), never a JSON number. `pricesInclude` may stay as stored or go back to `exclusive`; `inclusive` is refused ("Whether prices include sales tax can't be changed yet: documents add tax on top of prices."). `rounding` is `invoice` or `line`. Each state rule needs a US state code once, a jurisdiction (1 to 100 characters), a rate and a note (`rationale`) of at most 500. Each county rate needs a US state code, a county (1 to 60), a name (1 to 100) and a rate; no two rates for one county of a state, compared without case and without the word "County". A county rate with no rule under it is taken (it applies nowhere until a rule exists).
- **Taken for their shape only:** each rule's `validFrom`, `validTo` and `version`, each county rate's `id`, `validFrom` and `validTo`, and the company default's `validFrom`. The save sets them; no id a body sends ever selects a row.
- **Outer lengths.** The body is checked for shape first: types, unknown fields (400) and outer lengths, each refused with its field's shared words (each state 10, rounding and the prices setting 20, at most 51 rules and 200 county rates, the county 1,000, the company default's rate 100, filing and certificate types their own). The jurisdiction, name, rates and note have no outer length, because their words name a state or a county, and the never-stored id, dates and version none either; the JSON body limit bounds the request. Then `taxProblem` answers its first problem, with the demo's words and order.
- **Versions, never edits.** Each sent state rule is matched with the one in force by state, each county rate by state and county, never by id, and compared by value (rates with `sameOptionalDecimal`). An unchanged row is kept as it is, dates and version included. For a changed or removed state or county, every live row of it whose range reaches the company's day (`valid_to` empty or on or after it) ends the day before (`valid_to` and `updated_at` are the only columns ever updated); a changed or new row is inserted from that day with no end, a state rule with one above the highest version its state ever used (soft-deleted rows included), a county rate with a new uuid v7 id. Nothing is deleted. A second change on one day leaves the first that day with an empty range. The company default, stored in the `localization` row's `tax` block, is dated the company's day when it changes. Issued invoices keep their tax snapshot; nothing re-taxes them.
- **The save** locks the `localization` row (`FOR UPDATE`) and runs every check and every version number under that lock, so two saves serialize and the second is judged against the first's result. It stores the block without the rules and county rates (they live in `tax_rules` and `tax_jurisdictions`), and writes one `audit_log` entry in the same transaction: "Changed localization and tax", target "Sales tax", `before` and `after` the tab in force.
- **Who reads it.** `GET /settings` adds `localization.tax` for holders of `sales.quote.view` (the quote builder's tax preview and job-site states) or `settings.tax.manage`, not hidden by the `settings.localization` switch, as in force on the company's day: the block with, per state, the rule in force and, per county, the rate in force, sorted by state, then county. Rates are answered at the column's scale (`"8.81000000"`). Among rows valid on one day the latest `validFrom` wins, then the higher version, then the higher id, as in the tax engine.
- **The web.** `updateLocalization("tax", value)` sends the tab to its `PUT` and reads again, with no transport change (part 2a's routing and merge follow `API_LOCALIZATION_TABS`). The page runs `taxProblem` before the code dialog, shows the dates and the prices setting read only, and remounts the form after a save, so it shows what the save stored. Reset to default keeps filing and certificate types from the company's own copy; unchanged rows stay as they are, because rows are matched by state and county.

## Meetings (real build, ADR 0051)

Parts 1 to 3. These routes are in module `meetings` (403 `module_not_enabled` without it), in both products, and every one answers 404 when `meetings.calendar` is off.

- **Ids:** `:id` and `:attendeeId` are UUIDs. `:attendeeId` is the guest's `Attendee.id`: a linked guest's record id (the user id for staff), or an email guest's own row id. It is looked up only inside its own meeting.
- **Times** on the wire are the meeting's local `YYYY-MM-DDTHH:mm` (meetings.md). They are stored as instants in the company's zone, `tenants.time_zone`. Creating a meeting or a request in a company whose zone is not one of the seven US zones the calendar file knows answers 409 `time_zone_unsupported`.
- **Bodies** are strict. A rule's refusal is 400 `invalid_request` with the rule's own words.
- **Start bound** (review round 1 of PR #35): a start the caller sends (`POST /meetings`, a changed start in `PATCH /meetings/:id`, `POST /meeting-requests`, a proposal in `POST /meetings/:id/response`, an accepted proposal and a move's `start`) must lie from 366 days before the company's today to 1096 days after it, by local date. Otherwise 400 "Choose a start from one year ago up to three years ahead.", and nothing is written. A start the server derives, such as a series shifted by an `all` move, is not bounded.
- **Writes:** a change to an existing meeting locks it first. In the write's own transaction it works out what it will send from the state it commits, checks the daily email limits and writes its audit entry, whose `after.sends` holds `{ outside, total }`, the emails it sends. Invites, notices and the reminder are written after the commit; nothing after the commit can fail the request, and the reply is the meeting as the write committed it.
- **Daily email limits:** at most 200 emails to people outside the company (customers, suppliers, their people and email guests) and 500 meeting emails in all, per person per company day, every send counted, repeats included. They are counted from the person's meetings audit entries under a per-person lock, so actions sent at once count each other. An action over a limit is refused with 400 and writes nothing; one that sends nothing is never refused. A move, an undo and a decision count every email they send, re-sent occurrences and the CANCELs of a removed split included (part 2).
- **Every `Meeting` returned is shaped for the reader** (`meetingForViewer`):
  - the organiser, and anyone who may change the meeting, get every guest with their address;
  - anyone else gets only their own address, with an email guest named by an address read as "Email guest". With a hidden guest list they get only their own row;
  - other guests' notes and proposals go to the organiser only;
  - a customer, supplier or contact the reader can't read shows to every reader as "Customer", "Supplier", "Customer contact" or "Supplier contact", with no address.

"May change it" (`canChangeMeeting`) means holding `meetings.meeting.edit`, seeing the meeting, being able to read every customer, supplier and contact on it (the organiser included), and being its organiser or holding a scope wider than own on a meeting that is not private. A change emails every guest with the changer as the Outbox actor, and `GET /outbox` shows its actor the row whole, so someone who reads a guest only as "Customer" can't change the meeting. Otherwise the answer is 403: "Only someone who can see every guest on this meeting can change it." when that sight is all that is missing, and "Only the organiser can change this meeting." otherwise; 404 for someone who can't see the meeting.

| `GET /meetings/:id/calendar.ics` | `meetings.meeting.view` | `{ fileName, text }` as JSON, at the contract's path: METHOD:PUBLISH, no ATTENDEE, no STATUS, the current UID and SEQUENCE. ORGANIZER only for a reader who may read guests' addresses (the organiser and anyone who may change the meeting); anyone else's file has none. 404 when the reader can't see the meeting or it was cancelled |

- **Calendar files** carry `PRODID:-//Platform//Meetings//EN`:
  - STATUS:TENTATIVE while a request waits;
  - DTEND from the start instant plus the length;
  - an RDATE for a monthly series that starts after day 28;
  - only guests with a valid address, and only the recipient when the list is hidden or any guest is not staff, whatever the stored flag;
  - no REQUEST for a meeting that is already cancelled.
- **Invite emails** carry the file as a `text/calendar; method=<METHOD>` attachment (see "Notifications and Outbox").
- **Reminders** are scheduled Outbox rows for the next occurrence. They go to staff guests who are still members, never the organiser, and are dropped if not sent by the occurrence's start. A move, an undo and an accepted proposal re-sync them.
- **Undo answers** (part 2): 409 `meeting_changed` when the meeting, or a series the move split off, changed since the move, or the screen's SEQUENCE is not the one before it; 403 `forbidden` for anyone but the person who made the move; 409 `undo_expired` more than 5 minutes after the move. Since part 3 the SEQUENCE is checked before the mover, so a toast for an older move after someone else's newer one answers 409 `meeting_changed`, not 403. Also 400 `invalid_request` over a daily email limit, or when the undo, `this` included, would leave an occurrence already held at a date still ahead.
- **Audit:** a private meeting's entries name it "Private meeting", and no entry holds emails, notes or titles.
- **Not on the API yet:** Settings → Meetings. The server reads the stored group, or the safest defaults where a value is missing (15 minutes, proposals off, list hidden, new guests not saved).
- **Never on the API:** `simulateReply` and a delete route.
- **The web client** (part 3, `apps/web/src/lib/api/http/api-methods.ts`):
  - routes twelve methods: `meetingsData` and `myMeetings` (new), `createMeeting`, `updateMeeting`, `cancelMeeting`, `removeGuest`, `respondToMeeting`, `decideProposal`, `requestMeeting`, `meetingCalendarFile`, `rescheduleMeeting` and `undoReschedule`, each at the route above;
  - sends only what the server reads: a guest as `{ kind, id }`, a new guest as `{ email, name }`, a PATCH with only the fields the screen set, a request without length or place, a move as `{ meetingId, planned, start, durationMin, scope }`, and an undo as `{ sequence }`. The organiser is never sent as a guest;
  - `meetingsData` reads `GET /meetings`, `GET /meeting-guests` (403 or 404 → no guests) and, while `meetings.requests` and `meetings.invites` are on, `GET /me/meetings` (403 or 404 → no colleagues). The reader's id is `viewerUserId` of `GET /me/meetings`, or `user.id` of `GET /auth/context` only when that gave no answer. `newGuestHandling` is always `none`;
  - `myMeetings` reads `GET /me/meetings`, and a 403 or 404 there as nothing to show;
  - `simulateReply`, and `list` and `get` of `meetings` (read only by Simulate reply on the demo Outbox's rows), stay on DemoStore, as do the Outbox and the bell. Settings → Meetings is hidden in api mode until part 4, so `updateSettings("meetings")` is never sent;
  - after a routed write the server answered, a success or a 400, 403, 404, 409 or 422 refusal, the screens read again; a network failure, 401, 429 or 5xx triggers no re-read (since 2026-11-16 the rule for every routed write; see Conventions).

## Data import, part 1 (real build, ADR 0057)

Customers, customer addresses, suppliers and products. Both products, no class-level module: `settings.import.*` is in the always-on `platform` module, and each request's kind is checked against its own module. Every route needs `settings.import.manage`, answers 404 while `settings.import` is off, and carries `Cache-Control: private, no-store`. The behaviour is docs/product-spec/import.md, with the differences in its "Real build (ADR 0057)" section.

| Route | Status | Does |
| --- | --- | --- |
| `GET /imports` | 200 | `ImportOverview` `{ kinds, mappings, batches }`: the kinds this person may import here, in wizard order (none for an HR Suite company); the saved column choices of those kinds only; the newest 200 imports as `ImportBatchSummary` |
| `POST /imports/check` | 200 | The dry run. Body `ImportRequest` → `ImportPreview` `{ rows, counts }`. Writes nothing and makes no audit entry |
| `POST /imports` | 201 | The import, after a step-up. Body `ImportRequest` plus `expected` → `ImportResult` `{ batch, rows }` |
| `POST /imports/:id/undo` | 201 | Undo, after a step-up. No body → `ImportBatchSummary` with `undoneAt` and `undoneBy` |
| `PUT /imports/mappings/:kind` | 200 | Body `{ columns }` → `ImportMapping` `{ id, kind, columns, savedAt }`. Saved in place, one per kind |

- **Who:** `settings.import.manage` (route guard), data scope `all`, and every key of the kind: customers `customers.customer.view`, `.create`, `.edit`; addresses `customers.customer.view`, `.edit`; suppliers `purchasing.supplier.view`, `.create`, `.edit`; products `inventory.product.view`, `.create`, `.edit`, `.view_sensitive` and `purchasing.supplier.view`. A chosen `credit_limit` column needs `customers.customer.view_sensitive` (for suppliers also `inventory.product.view_sensitive` or `purchasing.bill.view`); `cost` is a required product column, so its key is a kind key. Undo checks the batch's kind and stored mapping the same way. Saving columns needs only the kind.
- **Switches:** `settings.import` (every route), then the records' own: `sales.customers` (customers, addresses), `purchasing.suppliers`, `inventory.products`. A kind whose switch is off is left out of `kinds` and answers 404. Stock, open invoices, bills, employees and timesheets answer 404 "This kind of import is not available." (later parts).
- **The request** carries only the chosen columns, in field order, with every row, so row numbers hold:

  ```json
  {
    "kind": "customers",
    "fileName": "customers.csv",
    "table": { "headers": ["Account Number", "Customer Name", "E-mail"], "rows": [["CUST-9001", "Maple Row Builders", "orders@maplerow.example"]] },
    "mapping": { "external_id": "Account Number", "name": "Customer Name", "email": "E-mail", "phone": null },
    "expected": "c"
  }
  ```

  `mapping` names only the kind's own fields (a header or null). `expected` is the dry run's action per row (`c` create, `u` update, `s` skip, `e` error), required on the import. The server parses no file and stores none; it reads every cell again with the shared `readCell`.
- **Limits:** 2,000 rows, 60 columns, 60 cells per row, cells of at most 1,000 characters, headers and file names of at most 200, each field's own length and digit caps, at most 60 column choices; a body of at most 100 KB (the parser's limit; the web refuses a larger one before sending); one dry run, import or Undo at a time per company; 50 imports per company in 24 hours (dry runs don't count).
- **The company** comes only from the session. Bodies are strict: a `companyId`, or any field the import doesn't take, is a 400. A batch id from another company is not found.
- **The import** runs in one transaction: the import lock, a 10-second lock timeout, the daily count, `SHARE ROW EXCLUSIVE` locks on the kind's tables (`lockStock` first for products), then the plan again against the records as they are. If any row's action differs from `expected`, nothing is written (409 `plan_changed`); otherwise every valid row is written, rows with errors are left out, and the batch is kept for Undo.
- **Undo** runs under the same import lock, lock timeout and table locks. It refuses, with nothing written and in this order, when a record differs from what the import wrote, for products when stock history or a removed earlier supplier stops it, or when a live record points at one the import created (foreign keys from the catalog, plus meeting guests, attachments, journal sources and outbox rows). Only then does it lock the rows it will soft-delete, `FOR UPDATE NOWAIT`: a quote or order line still being saved for one of them makes it answer 409 `import_busy` at once, never after a wait, so it can't deadlock with that writer; then it checks references again, so a link saved in between is counted. Created records are soft-deleted; updated ones get their earlier values back.
- **Audit:** one `data` entry per record created or updated ("Imported customer", "Updated customer by import"), one per batch ("Imported customers", with the counts text), the same on Undo ("Removed imported customer", "Restored customer after undoing an import", "Undid import"), and "Saved import columns". Credit limits and costs in entries, rows' `cells`, mappings and saved columns are stripped by name for anyone without their key. `import_jobs.changes` never leaves the server.

## Notifications and Outbox (real build, ADR 0032)

Each answers 404 when its feature (`shell.notifications`, `settings.outbox`) is off.

| Route | Needs | Does |
| --- | --- | --- |

Raising an event is server-side only (`NotificationService.notify`): modules call it when their records change. An Outbox row moves from `queued` (or `scheduled`) to `sent` or `failed`, and from `scheduled` to `cancelled`.

ADR 0051 added the following:
- **Calendar files:** a row's `.ics` attachments go with the email as UTF-8 `text/calendar; method=<METHOD>; charset=UTF-8` files, and a PDF kept only as a link stays in the text.
- **Expiry:** `notify` takes an optional `expiresAt`, kept in the row's values. A worker or Retry that claims the row after that time cancels it instead of sending it, so a meeting reminder never arrives after the meeting starts.
- **Caller's transaction:** `notify` and the new `cancelScheduled(event, source)`, which cancels one source's scheduled rows of one event, can run inside the caller's transaction.

## Errors and the simulated network

- Every failure a person should read is an `ApiError`. Reads surface it through `useApiQuery` (status `error`, with `retry`) and `QueryFallback`; a failed save that a screen does not catch is shown as a toast by `useApiErrorToasts`.
- `withStandingWatch` (`lib/api/standing-watch.ts`, ADR 0054) wraps the client inside the simulated network. A call that fails with an `HttpApiError` coded `company_maintenance`, `company_unavailable`, `company_suspended` or `company_read_only` tells the shell's `StandingGate` to read `getCompanyStanding()` again (one read in flight plus one trailing), and the same error is rethrown, so the screen handles it as before. `getCompanyStanding` and `getCompanyBilling` are never watched, so a refusal can't start a loop; the demo's errors are plain `ApiError`s and never signal.
- `withSimulatedNetwork` (`lib/api/network.ts`) wraps the client. The presenter guide's Network control sets normal, slow (each call waits 1.5 s) or offline (each call fails with an `ApiError` before it runs, so nothing is saved). It affects the next request only and resets on reload. `setViewer`, `subscribe`, `today` and `openCompany` are not simulated. A real client needs no change: the wrapper only delays or fails calls.
