## 2. Data model and migration

### 2.1 New and changed records

All types live in `packages/shared/src/types`; every change gets an ADR (one per batch, 0005 to 0011).

| Record | Change |
| --- | --- |
| `Location` (new collection `locations`) | `{ id, kind: "warehouse" \| "showroom", name, branchId, address, isDefault }`. Summit: Denver Central and Colorado Springs (warehouses), Summit Design Studio and Southgate Showroom. Keystone: Harrisburg Distribution and Lancaster Yard (warehouses), Front Street Showroom. Names and addresses invented. |
| `User` | `defaultLocationId: string \| null` (profile setting). |
| `Address` | Adds `county`, `lat`, `lng` (optional) for tax and suggestions. |
| `Customer` | `address` becomes `addresses: CustomerAddress[]` (`{ id, label: home \| billing \| job_site \| delivery, ...Address }`) with `defaultBillingId`, `defaultJobSiteId`; `profileComplete: boolean`. |
| `Quote` | Status draft / pending / accepted / converted / declined (expired is derived from `expiresAt`); adds `expiresAt`, `sentAt`, `locationId`, `taxOverride`. |
| `Invoice` | Removes stored `status` and `paid`. Keeps lifecycle facts only: `sentAt`, `voidedAt` + `voidReason`, `locationId`, `jobId`, `depositPct`, `taxSource`, `taxOverride`, `dueAt: string \| null` (null = balance held until installation). Credit notes stay `isReturn` with CR- numbers and gain `creditForInvoiceId`. |
| `Payment` | `{ number (PAY-0001), invoiceId, customerId, kind: payment \| deposit, amount, date, method: cash \| check \| ach \| card \| other, checkNumber?, cardLast4?, reference, note, files: FileMeta[], status: pending \| confirmed \| rejected \| voided, recordedBy/At, reviewedBy/At, rejectReason?, voidReason? }`. |
| `InvoiceAdjustment` (new) | `{ invoiceId, kind: write_off \| credit_applied, amount, reason, by, at, creditSourceId? }`. |
| `Refund` (new) | Outgoing refund of customer credit: method, reference, mandatory proof files, amount. |
| `FileMeta` | `{ id, name, type, size, uploadedBy, uploadedAt }` in the record; bytes in IndexedDB. |
| `StockMovement` (new collection `stockMovements`) | The stock ledger: `{ productId, rollId?, locationId, quantity (cartons, each, or roll ft), kind: opening \| receipt \| issue \| transfer_out \| transfer_in \| adjustment \| return, source: { kind, id } }`. On hand per warehouse is the sum. `Product.cartonsOnHand` is removed (derived). |
| `Roll` | `warehouse` text becomes `locationId`; keeps `bin`, `cuts` (each cut links its invoice). |
| `Reservation` (new) | `{ invoiceId, lineId, productId, rollId?, locationId, quantity, status: active \| released \| issued }`. Available = on hand − active reservations. |
| `Transfer` (new) | `{ number, fromId, toId, lines, status: in_transit \| received, sentAt, receivedAt }`. |
| `StockAdjustment` (new) | `{ productId \| rollId, locationId, delta, reason, note, status: approved \| pending_approval \| rejected }`. |
| `PurchaseOrder` | Status stored for draft / ordered / cancelled; partly received, received, billed, partly paid and paid are derived from receipts, bills and payments. Adds `locationId`, line `areaSqFt` for area goods. |
| `GoodsReceipt` (new collection `receipts`) | Per line: received, damaged, roll numbers, dye lots, lengths; receiving warehouse. |
| `Bill` | Removes stored `paid`; adds `receiptIds`, `matchIssues`, `files`. |
| `SupplierPayment` | Replaces `billPayments`: allocations `[{ billId, amount }]`, method, reference, proof files, status as customer payments. |
| `Supplier` | `terms: pay_on_order \| cod \| net_30 \| net_60 \| net_90 \| net_180 \| monthly_statement`, `creditLimit`. |
| `CommissionRule` (new) | `{ appliesTo: role \| user, basis: paid_revenue \| gross_margin, ratePct, tiers? }`. Earned commissions are computed from rules × confirmed payments; `CommissionPayout` records what was paid. The old stored monthly `commissions` collection goes. |
| `Meeting` | Adds `timeZone`, `until`, `exceptions` (per-occurrence moves or cancellations) for "this event / this and following / all". |
| `ImportBatch` (new) | Kind, file name, mapping, counts, created ids, previous versions of updated records (for Undo). Saved mappings per kind. |
| `DbConnection` (new) | Engine, host, port, database, user, SSL, mapping, schedule. Never a password. |
| `CompanySettings` | New sections: `tax` defaults (company rate, state defaults with effective dates, jurisdiction rules by county), `sales` (default waste % per category, quote expiry days), `payments` (approval on/off, threshold, write-off maximum, payment prefix), `inventory` (default warehouse, adjustment approval quantity, low-stock rule), `purchasing`, `commissions`. `areaUnit` gains `m2`. |

### 2.2 One ledger calculation

`packages/shared/src/ledger.ts` computes, from the records only: `paid` (confirmed payments), `pending`, credits applied, written off, `balance = total − confirmed − credits − write-offs` at full precision, the derived status (table in Appendix A), the labels Deposit paid and Overdue, and customer credit (overpayments + credit notes − applied − refunded). Invoices list, invoice page, customers, statement, dashboard, notifications, reports, PDF and quote view all call it; nothing else stores a paid or balance figure. Bills use the same module with supplier payments.

### 2.3 DemoStore migration

- The overlay gets `schemaVersion: 2`; storage keys move from `fp-demo:v1:` to `fp-demo:v2:`. On open, a v1 overlay found under the old prefix is upgraded by `lib/api/demo/migrations/v1-to-v2.ts`, then saved under v2 and the old keys are removed.
- Upgrades: settings sections are merged with the new defaults; customer `address` becomes one Home address marked default for billing and job site; roll `warehouse` text maps to the company's warehouses by name (Main warehouse → first, Annex → second); quote `sent` → `pending`, `invoiced` → `converted`; invoices drop `status` and `paid` (an invoice created in the demo has no payments yet; a voided one keeps `voidedAt`); bill payments become supplier payments with one allocation; stored roles rename `sales.payment.create` → `sales.payment.record` and `purchasing.bill.pay` → `purchasing.payment.record`; the Owner role and each stored ceiling gain the new keys their modules allow; default roles gain their new template keys.
- If any step throws, or a migrated record fails its type check, that company's overlay is dropped and the app shows one toast: "Your saved demo changes came from an older version of the demo, so this company was reset to fresh data." Table preferences tolerate missing fields.
- Reset demo data also clears the IndexedDB file store.

## 3. Assumptions and conflicts (Appendix B and more)

| Id | Assumption or conflict | Recommendation |
| --- | --- | --- |
| B-1 | Job complete moves the invoice forward (B6). | Agree. Sign-off is the "Complete" step: it sets Installed on the timeline, sets the held due date to completion + terms, marks the invoice sent, and adds a "Balance due after installation" notification for `sales.payment.record` holders. Keystone has no Installation module, so B6 is Summit only. |
| B-2 | Sales don't see waste by default. | Agree; `sales.waste.view` off for Sales, on for Owner, Manager, Accountant, Warehouse. |
| B-3 | Deposit paid is a label, not a stored status. | Agree; the ledger derives it. |
| C-1 | Reserve on issue, cut only after a confirmed deposit or payment. | Agree; override needs `inventory.reservation.override` (Owner, Manager) and a reason. If stock is short on issue, the invoice still issues and the line shows "Short by X, not reserved" instead of blocking the sale. |
| A-1 | Showrooms never hold sellable stock. | Agree; samples are a simple count per showroom shown on the location, not stock movements. |
| A-2 | Demo address provider by default; Google only with a key. | Agree. |
| G-1 | Live database connections run only in the full product. | Agree. |
| K-1 | **Receivables are not healthy today**: by count about 12% of invoices are overdue, as demo-spec section 4 asks, but by value 58% of Summit's open balance is overdue (30% over 90 days) and 42% of Keystone's (11%), because almost every recent invoice is already paid. B5 asks for under ~15% overdue by value and very little over 90 days. Appendix A also says seeded invoices keep their status after migration. | Regenerate the sales fixtures so recent invoices are still open and not yet due, and old overdue ones are mostly paid: overdue under 15% of the open balance, over 90 days under 3%, while keeping about 12% of invoices overdue by count. "Keep their status" then means: every Paid or Partly paid fixture invoice has matching payment records (the generator already writes them; the 12 returns have none and stay Returns), and a v1 browser overlay keeps its own invoices' status. E2e tests that pick a specific overdue invoice may need another record; each is named in its commit. |
| K-2 | **Permission key names**: the spec writes `payments.record`, `inventory.adjust`, `purchasing.view`, `import.manage`, `commissions.view_own` and so on, but every key in the app is `module.resource.action` and the matrix is built from that. | Keep the scheme and map: `sales.payment.{view, record, approve, void, refund, write_off, apply_credit}`, `sales.tax.override`, `sales.waste.view`, `inventory.stock.{adjust, approve}`, `inventory.transfer.{create, receive}`, `inventory.reservation.override`, `purchasing.order.{view, create, approve, receive}` (existing), `purchasing.bill.{view, create}` (existing), `purchasing.payment.{record, approve, void}`, `sales.commission.{view, manage}`, `settings.import.manage`, `settings.payments.manage`, `settings.locations.manage`. New actions join the action list. |
| K-3 | **Commissions view own / all**: the spec asks for two permissions, but the app already decides own / branch / all by data scope for every collection (commissions included). | One `sales.commission.view` that follows data scope: Sales see their own, Manager their branch, Owner and Accountant everything. Adding a second mechanism would break the spec's own "never a second way" rule. Commissions move from the HR module (`hr.commission.view`, unused in the UI) to Core. |
| K-4 | **Locations vs branches**: companies already have branches (data scope "branch", branch limit in super-admin), named "Denver showroom", "Lakewood warehouse" and so on. | Keep branches for data scope and limits; add locations (warehouses and showrooms) that each belong to a branch. Rename Summit's branches to Denver and Colorado Springs, and Keystone's to Harrisburg and Lancaster, so the names line up. |
| K-5 | **Company default tax rate vs "not collected"**: today a company collects only in states it has a rule for. A company default rate would tax every state. | The company default applies only in the company's states of operation (Region setting); outside them tax stays "not collected". Defaults carry taxability per category (materials and freight taxed, labor not) unless a rule says otherwise. Address county picks the jurisdiction rule. |
| K-6 | **Invoice drafts and editing**: Appendix A mentions Draft "if the app has this state" and locks lines after a confirmed payment, which implies lines can be edited before. B6 and C1 create invoices outside quotes. | No invoice drafts: an invoice is issued when created (from a quote, a job or a roll cut). Lines stay editable (reusing the quote lines editor) until the first confirmed payment; after that only a credit note changes it. |
| K-7 | **Deposit to** (Appendix A) asks for accounts "if the app has accounts". | The app has none, so the field is left out. |
| K-8 | **HEIC proofs**: Chrome cannot preview HEIC. | Accept PDF, JPG, PNG, WebP and HEIC by their real file signature; HEIC shows a file icon instead of a thumbnail. |
| K-9 | **Notifications** are derived, not stored. | Keep it that way: "3 payments to verify", "Job J-1042 completed: $X balance due", adjustments to approve and transfers to receive are new attention checks, gone once handled. |
| K-10 | **Every page needs a view permission** (A3), but several settings pages only have a `manage` key. | One page-permission map in the product config drives the menu, the route gate and the "You don't have access to this page" state. Settings pages use their `manage` key as the page key; no new settings `view` keys. |
| K-11 | **Moving a roll** today edits the warehouse as free text through `api.save`. | Move stays for a bin inside the same warehouse; another warehouse goes through a Transfer. The standalone Cut a roll palette action opens the invoice picker (C1). |
| K-12 | **US address list**: about 300 realistic addresses and "the US city and state list". | A curated list of about 250 US cities (every state, denser in the six tax states) with county, ZIP and approximate coordinates; 300 addresses generated from it with invented street numbers and common street names. Not every US city. |
| K-13 | **Area unit m²** (D1) is not an option today (sq ft, sq yd). | Add m² to the Region setting and `packages/shared/units`; storage stays sq ft. |
| K-14 | **Excel library**: the spec allows SheetJS from its CDN package or exceljs. | SheetJS from `cdn.sheetjs.com` (pinned tarball) in a Web Worker together with Papa Parse; ADR 0012. Both parse and write templates. |
| K-15 | **Calendar drag and resize**: no calendar library is listed. | Build on pointer events like the room canvas, with keyboard and form alternatives; no new dependency. |
| K-16 | **P&L basis**: the P&L is accrual (invoice dates) today. | Keep it accrual; the new Payments received report uses confirmed payment dates. |
| K-17 | **Existing tests**: changed on purpose. | Tests I expect to update, and why: invoice status filter and overdue checks (derived status, K-1 data), receivables aging on the customers page (moves to Reports, B5), Sales role payment permissions (record is off by default), cut roll from the roll page (now needs an invoice, C1), PO receive in one step (now a receipt form, D2), meetings week view (more views, F), fixture snapshot and reconciliation numbers. Each one is named in the commit that changes it. |
| K-18 | **Size**: the batch is roughly as large as the original demo. | Build in the order of the spec, committing and pushing after each item and ticking STATUS.md, so `/continue` can pick up across sessions. |

## 4. How each item is built

For every item: feature key in `packages/shared/src/features.ts` and a row in `docs/FEATURES.md` (new keys planned: `inventory.locations`, `inventory.transfers`, `inventory.adjustments`, `shell.tables`, `settings.access-preview`, `settings.tax-defaults`, `sales.payments`, `sales.team`, `reports.receivables`, `reports.payments`, `purchasing.receipts`, `purchasing.supplier-payments`, `settings.import`, `settings.database`, `shared.addresses`; existing keys change where the feature already exists), permission keys in the catalog and default roles, types and generator, ApiClient method and `docs/api-contract.md` row, DemoStore with a permission check inside the action, screen, unit tests in `packages/shared/test`, a Playwright spec and `screens.ts` entries, an ADR when the model changes, a `docs/blueprint-delta.md` row, then lint, typecheck, unit tests, commit, push, tick STATUS.md. The full suite runs at the end of each batch.

Papa Parse and SheetJS (G1), recorded in ADR 0012. Everything else uses the libraries already installed (TanStack Table, React Hook Form + Zod, Recharts, @react-pdf/renderer, date-fns, Motion).
